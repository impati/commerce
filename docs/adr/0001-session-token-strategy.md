# ADR-0001: 로그인 세션을 불투명 토큰으로 유지한다

- **상태:** 대체됨 — [ADR-0007](0007-hybrid-session-tokens.md)
- **날짜:** 2026-07-25
- **관련 커밋:** `50e5eec`, `6bd86d1`

## 배경

로그인을 도입하면서 요청 간에 신원을 이어갈 수단이 필요했다. 후보는 불투명 세션 토큰, JWT, JWE, 하이브리드 등이며 각각 무엇을 포기하는지가 다르다. 방식별 정리는 [problem/003](../../problem/003-session-mechanisms.md)에 있다.

이 저장소는 예제 수준에서 출발해 고도화 중이고, 실제 외부 호출과 운영 인프라는 붙이지 않되 도메인과 응용 계층은 완성 상태를 목표로 한다. 따라서 선택 기준은 "지금 구현이 쉬운 것"이 아니라 운영에서 무엇을 잃는지가 명확한 것이어야 한다.

## 결정

**로그인 세션을 불투명 토큰으로 유지하고, 게이트웨이가 요청마다 member-service에 물어 신원을 확인한다.**

- 토큰은 256비트 난수를 base64url로 인코딩한 문자열이다. 아무 의미도 담지 않는다
- 서버는 SHA-256 해시만 보관한다. 원문은 발급 시 한 번만 응답으로 나간다
- 게이트웨이가 `POST /members/internal/sessions/resolve`로 확인하고, 얻은 회원 식별자를 `X-Member-Id` 헤더로 하위 서비스에 넘긴다
- 하위 서비스는 토큰을 모르고 헤더만 신뢰한다

## 근거

폐기 즉시성을 가장 높은 우선순위로 두었다. 로그아웃, 비밀번호 변경, 계정 정지는 지연 없이 반영되어야 하며, 이것을 포기하면 대신 얻는 것보다 설명하기 어려운 사고가 생긴다.

JWT의 가장 큰 이점은 검증자가 발급자에게 물어볼 수 없는 상황에서 나온다. 이 저장소는 그 상황이 아니다.

| 판단 기준 | 이 저장소의 상황 |
| --- | --- |
| 검증자가 발급자에게 물어볼 수 있나 | 물어볼 수 있다. 같은 조직, 같은 배포 단위다 |
| 조직 경계를 넘는 검증이 있나 | 없다. 게이트웨이가 유일한 검증자다 |
| 요청당 조회가 병목인가 | 아니다. 그 규모가 아니다 |
| 폐기 즉시성이 필요한가 | 필요하다 |

표의 위 세 줄이 JWT를 택할 이유인데 셋 다 해당하지 않는다. 남은 한 줄이 불투명 토큰을 택할 이유이며 해당한다. 즉 이 저장소의 조건에서는 JWT의 이점이 실현되지 않고 대가만 남는다.

토큰 해시를 저장하는 이유는 별개다. 토큰은 그것을 가진 사람이 해당 계정으로 행세할 수 있으므로 비밀번호와 같은 급이다. 평문으로 보관하면 저장소를 읽을 수 있는 누구든 그대로 사용할 수 있고, 그 경로는 유출뿐 아니라 백업 파일, 쿼리 로그, 읽기 권한만 있는 내부자를 포함한다.

해시 함수로 SHA-256을 쓴 것도 별개의 판단이다. 비밀번호는 BCrypt를 쓰는데 토큰은 그렇지 않다. 토큰은 256비트 난수라 사전 공격이 성립하지 않으므로 느린 해시가 필요하지 않고, 무엇보다 **토큰 해시는 조회 키이므로 결정적이어야 한다.** BCrypt는 솔트 때문에 같은 입력도 매번 다른 값이 나와 조회에 쓸 수 없다.

## 전제

- 게이트웨이가 유일한 외부 진입점이다. 하위 서비스는 게이트웨이 뒤에만 있어야 한다
- 검증자와 발급자가 같은 조직에 있다
- 인증 트래픽이 member-service를 포화시키는 규모가 아니다

세 전제 중 하나라도 깨지면 이 결정을 다시 봐야 한다. 첫 번째는 현재 깨져 있다 — 아래 리스크 항목에 있다.

## 검토했으나 채택하지 않은 대안

- JWT 단독: 폐기 방법이 없다. 블랙리스트를 두면 매 요청 조회가 생겨 불투명 토큰과 같아지므로 이점이 사라진다. 키 배포·회전 부담과 알고리즘 confusion류 구현 취약점도 함께 들어온다
- JWE: 검증자가 복호화 키를 가져야 하므로 공개키 검증이라는 JWT의 이점이 사라진다. 감출 값이 필요하지 않은 상황에서 비용만 늘어난다
- Access token + refresh token 하이브리드: 요청당 조회를 없애면서 폐기를 refresh 쪽에만 남기는 구성이다. 이 저장소의 현재 규모에서는 얻는 것이 없고, 폐기가 "즉시"에서 "수명 내"로 약해진다. 다만 발급자 장애 결합이 문제가 되면 이 방향이 답이다
- 세션 쿠키: 전달 방식의 차이일 뿐 저장 구조는 불투명 토큰과 같다. `HttpOnly`로 XSS 표면을 줄이는 이점이 있어 후속으로 검토 중이다 ([BL-0005](../backlog/bl-0005-token-storage-to-cookie.md)). 대신 CSRF 대응이 따라온다
- PASETO: 알고리즘 협상을 없애 구현 취약점을 줄이지만 폐기 문제는 JWT와 같다. 생태계가 작다
- mTLS 클라이언트 인증서: 최종 사용자에게 인증서를 배포·갱신할 수 없다

## 이 결정이 만든 리스크

**발급자 장애가 전체 인증 장애가 된다.** member-service가 죽으면 이미 로그인한 사용자의 모든 요청이 실패한다. 상품 조회처럼 인증이 없는 경로는 살아 있고 장바구니와 주문은 전부 막힌다. 캐시를 붙이면 지연은 줄지만 미스 시에는 여전히 의존하므로 결합 자체는 남는다.

요청당 홉이 하나 붙는다. 현재 규모에서는 문제가 아니지만 캐시가 없는 상태다.

전제가 깨져 있는 항목이 하나 있다. 서비스가 8101~8109로 직접 노출돼 있어 게이트웨이를 우회하면 `X-Member-Id`를 위조할 수 있고, TLS 종료 이후 구간이 평문이므로 헤더를 읽을 수도 있다. 이 결정은 게이트웨이가 유일한 진입점이라는 전제에 서 있으므로 그 전제를 코드로 강제해야 한다. [BL-0001](../backlog/done/bl-0001-gateway-bypass-block.md)이다.

> 2026-08-16 후속: [ADR-0002](0002-network-segmentation-as-trust-boundary.md)에서 이 전제를 코드가 아니라 배포 토폴로지로 강제하기로 결정했다. 로컬에서 포트가 열려 있는 것은 운영 토폴로지가 아니며, BL-0001은 그 결정으로 닫혔다. 위 문장은 그때의 판단으로 남긴다.

## 재검토 조건

다음 중 하나가 성립하면 이 결정을 다시 본다.

| 조건 | 그때의 방향 |
| --- | --- |
| member-service 장애가 전체 인증을 끊는 것이 실제 문제가 된다 | 하이브리드. access token 수명이 폐기 지연 상한이 된다 |
| 조직 경계를 넘는 검증이 생긴다 (외부 파트너, 다른 팀의 API) | JWT. 그쪽은 우리 저장소를 조회할 수 없다 |
| 인증 트래픽이 member-service를 포화시킨다 | 먼저 캐시, 그다음 하이브리드 |
| 권한 정보를 서비스마다 판단해야 한다 | 토큰에 클레임을 담는 방향. 담을 값의 노출 범위를 함께 정한다 |

## 미해결

- 세션 확인 캐시의 TTL을 정하지 않았다. 그 값이 폐기 지연 상한이 되므로 보안 요구와 함께 정해야 한다
- 프론트가 토큰을 `localStorage`에 보관한다. XSS로 읽히므로 `HttpOnly` 쿠키가 맞고, CSRF 대응을 함께 설계해야 한다
