# ADR-0006: 이메일 확인 토큰을 URL 프래그먼트로 옮긴다

- **상태:** 승인됨
- **날짜:** 2026-08-23
- **해결한 백로그:** BL-0002 인증 링크 토큰의 Referer 유출
- **관련:** [PD-0001](../policy/pd-0001-signup-and-email-verification.md), [problem/004](../../problem/004-secrets-in-url.md)

## 맥락과 의도

이메일 확인 링크가 토큰을 쿼리스트링에 담았다 — `http://localhost:5173/verify?token=...`.

**URL은 비밀을 담는 그릇이 아니다.** URL은 목적지를 나타내는 주소이며, 그래서 웹 서버는 요청 URL 전체를 접근 로그에 기록한다. nginx의 기본 로그 포맷이 그렇고 CDN·로드밸런서·WAF도 마찬가지다. 이것은 설정 실수가 아니라 기본 동작이다.

그 결과 확인 토큰이 평문으로 접근 로그에 남는다. 무게는 세 가지에서 온다.

**로그가 토큰보다 오래 산다.** 토큰 수명은 24시간이고([PD-0001-R6](../policy/pd-0001-signup-and-email-verification.md)) 접근 로그 보관은 통상 수 주에서 수 년이다.

**로그 접근 권한이 DB 접근 권한보다 넓다.** 로그는 수집기로 흘러가고 백업되고 장애 분석 때 덤프로 공유된다.

**토큰이 소진되지 않은 채 로그에 남는 경우가 흔하다.** 정상 클릭이면 로그가 찍히고 수백 밀리초 뒤 소진되지만, 메일 보안 스캐너와 링크 미리보기(Outlook Safe Links, Slack 언펄)는 URL을 가져가면서 JS를 실행하지 않는다. JS 로드 실패나 즉시 탭 닫기도 같다. 이 경우 토큰은 로그에 남은 채 만료까지 유효하다. 기업 메일 환경에서 링크 스캐너는 예외가 아니라 기본이다.

**저장 시점과 앞뒤가 맞지 않는다는 점이 결정적이다.** [RegistrationExecutor](../../apps/member-service/src/main/java/com/impati/commerce/member/application/component/RegistrationExecutor.java)는 DB에 토큰 원본이 아니라 해시를 저장한다. 비밀번호를 다루는 방식이며, 이 토큰이 DB 유출에도 견뎌야 하는 비밀이라고 이미 판단한 것이다. 그렇게 감춘 원본이 접근 로그에는 평문으로 박힌다.

지금 이 토큰이 하는 일은 `activate()` 하나이므로 유출 피해는 계정 선점 수준으로 제한된다. 그러나 `/verify?token=` 이라는 형태는 **다음에 비밀번호 재설정이나 매직 링크가 놓일 자리**이며, 그때 같은 유출 경로는 계정 탈취가 된다. 지금 바로잡는 비용은 파일 두 개이고 나중 비용은 이미 발송된 링크와 축적된 로그 전부다.

## 결정

**확인 링크가 토큰을 URL 프래그먼트에 담는다.** `?token=`을 `#token=`으로 바꾼다.

프래그먼트는 **브라우저가 서버로 전송하지 않는다.** 문서 내 위치를 가리키는 것이라 서버가 알 필요가 없기 때문이며, 규격상 요청 라인에 포함되지 않는다. 따라서 접근 로그에 남지 않는다. 같은 이유로 `Referer` 헤더에서도 제거된다.

**프론트는 프래그먼트만 읽는다. 쿼리 하위 호환을 두지 않는다.** 형식을 바꾸면 그 전에 발송된 링크가 만료까지 깨지므로 보통은 양쪽을 한동안 받아야 한다. 여기서는 두지 않는데, **이 저장소에 배포된 인스턴스가 없어 유효한 구 형식 링크가 존재하지 않기 때문이다.** 없는 호환을 위해 코드를 남기면 제거를 강제할 장치 없이 부채만 남는다.

이 근거는 운영 인스턴스가 생기는 순간 사라진다. 그때는 확인 링크의 형식을 바꾸는 모든 변경에 **하위 호환 읽기 또는 조율된 배포**가 따라붙어야 한다. 어느 쪽도 없으면 전환 구간에 발송된 링크가 반드시 깨진다 — 백엔드를 먼저 올리면 구 프론트가 새 형식을 못 읽고, 프론트를 먼저 올리면 새 프론트가 구 형식을 못 읽는다.

**링크 형식을 고정하는 테스트를 둔다.** 지금은 `#`를 `?`로 되돌려도 하네스가 통과한다. 이 결정을 유지하는 것은 문서가 아니라 테스트다.

## 고려한 선택지

### `Referrer-Policy: no-referrer`를 함께 넣는다 — 채택하지 않음

백로그 항목이 원래 제안한 순서다("먼저 헤더로 막고, 프래그먼트 전환은 별도로 판단한다"). 채택하지 않은 이유는 둘이다.

**헤더가 막는 경로를 프래그먼트가 이미 막는다.** 프래그먼트는 Referer에 실리지 않으므로, 토큰이 프래그먼트에 있는 이상 Referer로 나갈 토큰 자체가 없다.

**헤더가 막으려던 경로는 이미 브라우저 기본값이 막고 있다.** 백로그가 지목한 것은 [App.tsx](../../frontend/storefront/src/App.tsx)가 `images.unsplash.com`에서 상품 이미지를 로드할 때 붙는 크로스오리진 Referer였다. 그러나 주요 브라우저의 기본 참조자 정책은 `no-referrer-when-downgrade`에서 `strict-origin-when-cross-origin`으로 바뀌었고(Chrome 85, Firefox 87), 이 정책은 크로스오리진 요청에 오리진만 보낸다. 경로와 쿼리가 이미 제거된다.

**받아들인 위험은 "기본값은 보장이 아니다"** 라는 것이다. CDN이 `Referrer-Policy`를 느슨한 값으로 내려주거나 개별 요소에 `referrerpolicy="unsafe-url"`이 붙으면 정책이 조용히 되돌아간다. 다만 그 경우에도 프래그먼트에 있는 토큰은 새지 않으므로, 되살아나는 것은 유출 경로이지 이 토큰의 유출은 아니다. 정적 호스트 설정이 생기는 시점을 재검토 조건으로 둔다.

### 토큰을 링크에서 빼고 확인 코드를 입력받는다 — 채택하지 않음

메일에 짧은 코드를 적고 사용자가 화면에 입력하면 URL을 아예 쓰지 않으므로 모든 경로가 사라진다. 그러나 클릭 한 번이 타이핑으로 바뀌어 가입 이탈률이 오른다. **사용자 경험을 바꾸는 제품 결정이므로 기술 결정으로 처리하지 않는다.** 필요해지면 정책으로 다룬다.

### 링크를 짧은 수명의 일회성 리다이렉트로 감싼다 — 채택하지 않음

메일에는 랜덤한 조회용 식별자만 담고 서버가 그것을 실제 토큰으로 교환하는 방식이다. 유출 표면은 줄지만 교환용 식별자 역시 URL에 있어 같은 문제를 한 단계 미룰 뿐이고, 저장소와 만료 관리가 하나 더 늘어난다. 프래그먼트가 같은 목적을 더 적은 구조로 달성한다.

### 아무것도 하지 않는다 — 채택하지 않음

현재 피해가 계정 선점으로 제한된다는 점은 사실이다. 그러나 이 저장소는 현재 코드의 미완성 상태를 설계 근거로 쓰지 않기로 정했고, 운영 서비스에서 인증 토큰을 쿼리스트링에 두는 것은 성립하지 않는다.

## 범위

- **포함:** [NotificationExecutor](../../apps/notification-service/boot/api/src/main/java/com/impati/commerce/notification/application/component/NotificationExecutor.java)의 링크 조립, [App.tsx](../../frontend/storefront/src/App.tsx)의 파싱, 링크 형식을 고정하는 테스트
- **제외:** `Referrer-Policy` 헤더, 확인 코드 입력 방식, `history.replaceState` 타이밍(유출 경로 중 브라우저 이력은 이번 대상이 아니다), 정책 문서(PD-0001의 규칙 열 개는 그대로 참이며 토큰의 전달 형식만 바뀐다)

## 완료 기준

- `make verify` 통과, `make frontend-build` 성공
- 확인 링크가 `#token=` 형식임을 고정하는 테스트가 있고, `?`로 되돌리면 실패한다
- 프론트가 `#token=`으로 확인을 완료한다

## 위임된 결정

- 테스트 클래스·메서드 이름, 주석 문구, 토큰을 꺼내는 코드의 형태
- 기본 방침은 기존 파일의 톤과 구조를 따르는 것

## 결과와 제약

**얻는 것.** 확인 토큰이 우리 서버와 중간 경로의 접근 로그에 남지 않는다. Referer로 나갈 수 있는 형태가 사라져 참조자 정책 변화에 영향받지 않는다. 토큰을 저장 시점과 전달 시점에서 같은 무게로 다루게 된다.

**받아들인 트레이드오프.** 확인 링크의 형식이 프론트와 notification-service 양쪽에 걸쳐 있어 한쪽만 바꾸면 깨진다. 링크 형식 테스트가 백엔드 쪽만 고정하므로 프론트가 어긋나는 것은 잡히지 않는다.

**남은 위험.**

1. **브라우저 이력과 사람의 복사는 그대로다.** 프래그먼트도 주소창에 뜨고 이력에 들어간다. `history.replaceState`가 지우지만 JS 실행 이후이므로 실패하면 남는다. 유출 경로 C는 이번 범위 밖이다.
2. **하위 호환을 두지 않은 근거가 저장소 상태에 걸려 있다.** 배포된 인스턴스가 없다는 사실이 전제이며, 그것이 바뀌면 이 결정의 일부가 함께 바뀐다.
3. **링크 스캐너가 토큰을 소진하는 문제는 그대로다.** 프래그먼트는 스캐너가 토큰을 보는 것을 막지만, 스캐너가 JS를 실행하는 경우의 소진은 막지 않는다. 별도 문제다.

## 재검토 조건

- 프론트를 서빙하는 정적 호스트·CDN 설정이 저장소에 생길 때. 그 시점에 `Referrer-Policy`를 응답 헤더로 명시할지 다시 판단한다. 채택하지 않은 이유가 "브라우저 기본값이 막는다"였고, 그 기본값을 덮어쓸 수 있는 자리가 바로 거기다.
- 비밀번호 재설정이나 매직 링크처럼 **세션을 발급하는 토큰**을 링크로 보내게 될 때. 피해 크기가 달라지므로 이력·복사 경로까지 다뤄야 한다.
- 메일 클라이언트가 프래그먼트를 보존하지 않는 사례가 관측될 때. 일부 리다이렉트 래퍼는 프래그먼트를 떨어뜨린다.
- 운영 인스턴스가 생길 때. 하위 호환을 두지 않은 근거가 그 시점에 사라지므로, 이후 확인 링크 형식을 바꾸는 변경에는 하위 호환 읽기나 조율된 배포가 필요하다.
