# ADR-0007: 세션을 단명 서명 토큰과 장수명 세션으로 나눈다

- **상태:** 승인됨
- **날짜:** 2026-08-23
- **대체:** [ADR-0001](0001-session-token-strategy.md) 로그인 세션을 불투명 토큰으로 유지한다
- **해결한 백로그:** BL-0003 세션 확인의 가용성 결합과 지연
- **관련:** [PD-0014](../policy/pd-0014-login-rejection-and-session-lifetime.md), [ADR-0002](0002-network-segmentation-as-trust-boundary.md), [BL-0045](../backlog/done/bl-0045-tolerate-member-service-outage.md)

## 맥락과 의도

[ADR-0001](0001-session-token-strategy.md)은 로그인 세션을 불투명 토큰으로 두고 게이트웨이가 요청마다 member-service에 물어 신원을 확인하게 했다. 폐기 즉시성을 가장 높은 우선순위로 둔 결정이었고, 그 문서는 자기가 만든 리스크를 스스로 적어 두었다.

> **발급자 장애가 전체 인증 장애가 된다.** member-service가 죽으면 이미 로그인한 사용자의 모든 요청이 실패한다.

그리고 재검토 조건에 방향까지 적었다 — "member-service 장애가 전체 인증을 끊는 것이 실제 문제가 된다 → 하이브리드. access token 수명이 폐기 지연 상한이 된다."

**그 조건이 성립했다고 판단한다.** 조사에서 드러난 것이 셋이다.

**대가는 치르고 있는데 이득은 일부만 걷고 있었다.** ADR-0001의 근거 문단은 "로그아웃, 비밀번호 변경, 계정 정지는 지연 없이 반영되어야 한다"고 셋을 들었다. 실제로 존재하는 것은 로그아웃 하나이고, 나머지 둘은 기능이 없다. 게다가 세션 확인이 회원 상태를 보지 않으므로 계정 정지를 붙여도 이 구조에서 반영되지 않는다 ([BL-0044](../backlog/bl-0044-session-resolve-ignores-member-status.md)).

**즉시성이 사주는 값을 다시 계산했다.** 폐기가 필요한 상황의 전체 노출은 인지·대응·전파의 합이고 앞의 둘이 압도한다. 이 판단으로 폐기 상한을 정상 5분으로 정했다 ([PD-0014-R8](../policy/pd-0014-login-rejection-and-session-lifetime.md)). **정책이 즉시성을 요구하지 않게 된 이상 이 구조를 유지할 근거가 사라진다.**

**요청당 조회는 지연과 부하이기도 하다.** 인증이 필요한 모든 요청에 홉이 하나 붙고 캐시가 없다.

## 결정

**세션을 둘로 나눈다. 게이트웨이가 검증하는 것은 서명된 단명 토큰이고, 상태를 갖는 것은 기존 세션이다.**

| | access token | 세션 (refresh 역할) |
| --- | --- | --- |
| 형태 | 서명 토큰 (JWT) | 불투명 토큰 — **지금 것 그대로** |
| 수명 | 5분 ([PD-0014-R8](../policy/pd-0014-login-rejection-and-session-lifetime.md)) | 14일 ([PD-0014-R4](../policy/pd-0014-login-rejection-and-session-lifetime.md)) |
| 검증 주체 | 게이트웨이가 **로컬에서** | member-service가 저장소 조회로 |
| 호출 빈도 | 요청당 (조회 없음) | 5분당 한 번 |

**`Session` 도메인과 `member_sessions` 테이블은 그대로 둔다.** 지금 "세션 토큰"이라 부르던 것이 갱신 자격증명 역할을 그대로 맡는다. 개념이 바뀌지 않으므로 — 장수명 자격증명이고, 폐기 가능하고, 해시로 저장한다 — 새 타입이나 마이그레이션을 만들지 않는다. **PD-0014의 R3·R4·R5가 세션에 대한 규칙 그대로 성립한다.**

**폐기는 세션에만 건다.** 로그아웃하면 세션이 폐기되고, 이미 발급된 access token은 남은 수명 동안 동작한다. 5분 뒤 갱신하러 오면 거절된다. **access token 수명이 곧 폐기 지연 상한이며 두 값은 같은 값이다.**

**서명은 공개키 방식으로 한다.** member-service가 개인키로 서명하고 게이트웨이는 공개키로 검증만 한다.

게이트웨이는 유일한 퍼블릭 인그레스이며([ADR-0002](0002-network-segmentation-as-trust-boundary.md)) 가장 먼저 침해되는 자리다. **대칭 키를 쓰면 검증 키가 곧 발급 키이므로 게이트웨이 침해가 임의 신원 위조가 된다.** 공개키면 침해당해도 위조할 수 없다. 비용 차이는 설정 수준이다.

**access token에는 회원 식별자와 시각 정보만 담는다.** 서명은 위조를 막을 뿐 내용을 감추지 않으므로 담은 것은 모두 읽힌다. 권한을 담지 않는 이유는 따로 있다 — **담으면 폐기 지연이 권한 변경에도 적용된다.**

**서명 라이브러리를 쓰고 직접 만들지 않는다.** ADR-0001이 JWT의 비용으로 지목한 알고리즘 confusion류 취약점이 직접 만들 때 정확히 생기는 것이다.

## 고려한 선택지

### 짧은 TTL 캐시 — 채택하지 않음

게이트웨이가 토큰과 회원 식별자의 대응을 짧은 TTL로 기억한다. 변경이 가장 작고 지연과 부하를 크게 줄인다.

**그러나 목표를 달성하지 못한다.** 캐시는 기억한 항목만 안다. 미스에서는 여전히 member-service에 의존하고, 게이트웨이가 재시작하면 전부 잃으며, 장애 중에 로그인한 적 없는 사용자는 인정할 근거가 없다. 결합이 남는다.

이 차이는 [BL-0045](../backlog/done/bl-0045-tolerate-member-service-outage.md)에서 결정적이 된다. "장애 판정 중 24시간 인정"([PD-0014-R9](../policy/pd-0014-login-rejection-and-session-lifetime.md))을 캐시로는 지킬 수 없다 — 인정할 신원을 게이트웨이가 들고 있지 않기 때문이다. 서명 토큰은 게이트웨이가 아무 상태 없이 검증하므로 전원이 동작한다.

### 대칭 키(HMAC) 서명 — 채택하지 않음

검증자가 게이트웨이 하나뿐이므로 키를 나눠 갖는 실질적 부담이 없고 설정이 단순하다. 채택하지 않은 이유는 위에 적은 대로 **게이트웨이의 노출도**다. 검증만 필요한 곳에 발급 능력을 주지 않는다.

### JWT 단독 (세션 없이) — 채택하지 않음

ADR-0001이 이미 거절했고 그 판단은 지금도 유효하다. 폐기할 방법이 없고, 블랙리스트를 매 요청 조회하면 불투명 토큰과 같아져 이점이 사라진다. 하이브리드는 폐기를 세션 쪽에 남겨 이 문제를 피한다.

### refresh token 교체(rotation) — 지금 하지 않음

갱신할 때마다 세션 토큰을 새로 발급하고 이전 것을 폐기하면, 같은 토큰이 두 번 쓰이는 것이 탈취 신호가 된다.

지금 하지 않는 이유가 둘이다. **탐지의 값이 대응에서 나오는데 그 대응이 없다** — 탈취를 감지해도 해당 회원의 세션을 한꺼번에 끊는 수단이 없고, 그것은 [BL-0044](../backlog/bl-0044-session-resolve-ignores-member-status.md)가 다룰 영역이다. 그리고 **네트워크 재시도로 같은 토큰이 두 번 도착하는 정상 상황을 탈취로 오판하면 실제 사용자가 끊긴다.** 경합 처리를 함께 설계해야 제대로 되는 기능이다.

세션 토큰 보호는 `HttpOnly` 쿠키로 옮기는 쪽([BL-0005](../backlog/bl-0005-token-storage-to-cookie.md))이 먼저 값을 낸다. 지금은 `localStorage`에 있어 XSS로 읽힌다.

### 공개키 배포(JWKS) 엔드포인트 — 지금 만들지 않음

member-service가 공개키를 HTTP로 노출하고 게이트웨이가 주기적으로 가져오면 키 회전이 자동화된다. 검증자가 하나뿐이고 키 회전 절차 자체가 아직 없으므로 지금은 설정 주입으로 충분하다. 검증자가 늘거나 회전 주기를 정할 때 다시 본다.

## 범위

- **포함:** access token 발급 포트와 어댑터, 로그인 응답 확장, 갱신 유스케이스, 게이트웨이의 로컬 검증 전환, 프론트의 토큰 두 개 보관과 갱신 흐름, 각 계층 테스트
- **제외:** 장애 판정과 24시간 스테일 허용([BL-0045](../backlog/done/bl-0045-tolerate-member-service-outage.md)), rotation, JWKS, 쿠키 전환([BL-0005](../backlog/bl-0005-token-storage-to-cookie.md)), 회원 상태 확인([BL-0044](../backlog/bl-0044-session-resolve-ignores-member-status.md)), 키 회전 절차

## 완료 기준

- `make verify` 통과, `make frontend-build` 성공
- **게이트웨이가 인증이 필요한 요청을 처리하면서 member-service를 부르지 않는다**는 것을 고정하는 테스트가 있다. 이 작업의 핵심 단언이다
- 위조된 서명과 만료된 access token이 거부된다
- 폐기된 세션으로는 갱신되지 않는다
- 검증 로직을 무력화하면 위 테스트가 실패하는 것을 확인한다

## 위임된 결정

- 포트와 클래스 이름, 클레임 이름, 설정 키 이름, 테스트 구성, 프론트 갱신 묶기 방식
- 기본 방침은 기존 파일의 구조와 명명 규칙을 따르는 것. 포트 이름에 수단을 넣지 않는다

## 결과와 제약

**얻는 것.** 게이트웨이가 access token 수명 동안 member-service 없이 동작한다. 인증이 필요한 요청에서 홉이 사라져 지연과 부하가 준다. [BL-0045](../backlog/done/bl-0045-tolerate-member-service-outage.md)가 얹힐 토대가 생긴다.

**받아들인 트레이드오프.** 폐기가 최대 5분 늦는다([PD-0014-R5](../policy/pd-0014-login-rejection-and-session-lifetime.md), [R8](../policy/pd-0014-login-rejection-and-session-lifetime.md)). 키를 두 서비스가 나눠 갖는 운영 요소가 생긴다. 프론트에 갱신 흐름과 그 동시성 처리가 생긴다.

**남은 위험.**

1. **이번 작업 후 장애 내성은 5분이다.** 실제 장애는 대개 그보다 길다. [BL-0045](../backlog/done/bl-0045-tolerate-member-service-outage.md) 전까지는 목표가 절반만 달성된 상태다.
2. **개인키가 유출되면 임의 신원을 위조할 수 있다.** 지금 구조에는 없던 종류의 단일 실패점이며, 회전 절차가 없으므로 유출 시 대응이 정해져 있지 않다.
3. **프론트의 갱신 흐름을 하네스가 검증하지 못한다.** 이 저장소에 프론트 테스트 러너가 없어 타입 검사까지가 상한이다. 동시 요청이 갱신을 여러 번 일으키는 결함은 수동 확인으로만 잡힌다.
4. **세션 토큰이 여전히 `localStorage`에 있다.** 수명이 14일이라 탈취 피해가 access token보다 크다 ([BL-0005](../backlog/bl-0005-token-storage-to-cookie.md)).

## 재검토 조건

- **검증자가 늘어날 때.** 다른 엣지나 외부 파트너가 토큰을 검증하게 되면 JWKS 배포와 키 회전을 함께 정해야 한다.
- **세션 토큰 탈취가 관측되거나 쿠키 전환이 끝날 때.** rotation을 지금 하지 않은 근거 중 하나가 "쿠키가 먼저"였다.
- **회원의 모든 세션을 한꺼번에 끊는 수단이 생길 때** ([BL-0044](../backlog/bl-0044-session-resolve-ignores-member-status.md)). rotation의 탐지가 그때 값을 갖는다.
- **자동 탐지가 폐기를 일으키게 될 때.** [PD-0014](../policy/pd-0014-login-rejection-and-session-lifetime.md)의 재검토 조건과 같다 — 5분 상한이 무너지면 access token 수명도 함께 바뀐다.
- **권한을 서비스마다 판단해야 할 때.** 토큰에 클레임을 담는 방향이 다시 검토 대상이 되며, 담는 값의 노출 범위와 폐기 지연을 함께 정해야 한다.
