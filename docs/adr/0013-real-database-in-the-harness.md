# ADR-0013: 실제 DB 위에서 검증한다

- **상태:** 승인됨
- **날짜:** 2026-08-29
- **해결한 백로그:** BL-0053 인프라를 컨테이너로 세우고 실 DB로 옮긴다
- **관련:** [ADR-0009](0009-reconcile-unconfirmed-payments.md), [ADR-0011](0011-deliver-verification-mail-once.md), [ADR-0012](0012-order-events-as-outbox.md), [PD-0001](../policy/pd-0001-signup-and-email-verification.md)

## 맥락과 의도

저장소를 가진 여덟 서비스가 H2 위에서만 돌았다. H2는 자바 라이브러리라 테스트 프로세스 안에서 뜨고, 그래서 하네스가 외부 프로세스 없이 돌았다. 편했지만 **운영에서 쓸 DB의 동작이 한 번도 검증되지 않았다.**

가장 위험한 지점은 점유였다. [ADR-0011](0011-deliver-verification-mail-once.md)과 [ADR-0012](0012-order-events-as-outbox.md)가 `for update skip locked` 위에 배타성을 세웠는데, 이 구문의 잠금 범위와 격리 수준별 동작은 DB마다 다르다. H2에서 통과한다는 것이 운영 DB에서 같게 돈다는 근거가 되지 않는다.

이 저장소는 같은 실수를 반복해서 겪었다. `./gradlew test`가 두 달간 실행조차 되지 않던 상태에서 하네스를 세운 것이 출발점이었고, `docker-compose.yml`은 지금도 한 번도 실행된 적이 없다. **검증되지 않는 경로는 반드시 샌다.**

## 결정

### 여덟 서비스를 MySQL 8로 옮기고, 테스트도 그 위에서 돈다

대역(H2)으로 검증하고 운영에서 다른 DB를 쓰면 검증되지 않은 경로를 하나 더 만드는 것이다. 어댑터만 갈아끼우면 나갈 수 있는 상태를 목표로 하는 이 저장소에서, **DB는 갈아끼울 어댑터가 아니라 그 어댑터가 말을 거는 상대다.**

**8.0.16 이상을 고정한다.** inventory가 재고 음수 방지에 `check` 제약을 쓰는데, 그 아래 버전은 제약을 파싱만 하고 **강제하지 않는다.** 조용히 통과하는 검증은 없는 것보다 나쁘다.

### 격리는 스프링 컨텍스트마다 데이터베이스로 만든다

컨테이너 하나를 모든 테스트가 공유하고 컨텍스트마다 데이터베이스를 따로 만든다.

H2에서는 컨텍스트마다 별개의 in-memory DB를 썼고, 그래서 테이블을 통째로 비우는 테스트가 다른 컨텍스트를 깨뜨리지 않았다. **DB를 옮기면서 그 성질을 부수면 원인 모를 실패가 나중에 생긴다.** 격리를 만드는 것은 데이터베이스이지 컨테이너가 아니므로, 컨테이너를 늘릴 이유는 없다.

**테스트가 선언하지 않는다.** `ContextCustomizerFactory`를 `spring.factories`로 등록해 모든 테스트 컨텍스트에 자동으로 붙인다. 테스트가 직접 부르게 두면 빠뜨렸을 때가 조용하다 — 붙이지 않으면 `application.properties`의 기본값으로 떨어져 **개발자의 로컬 개발 DB에 연결되고**, 그 테스트는 실패하는 대신 실제 데이터를 건드린다. 규율에 맡길 수 없는 종류다.

커스터마이저가 테스트 클래스를 값으로 갖는 것이 격리를 만든다. 스프링은 그 동등성으로 컨텍스트를 캐시하므로, 클래스가 다르면 컨텍스트가 합쳐지지 않고 데이터베이스도 합쳐지지 않는다.

**만들기 전에 같은 이름을 지운다.** 컨테이너를 재사용하면 일련번호는 JVM마다 0에서 시작하는데 컨테이너는 실행을 넘어 살아남는다. 지우지 않으면 두 번째 실행이 이미 있는 이름을 만들려다 실패하거나 지난 실행의 데이터를 물려받는다. 실행이 끝나면 이번에 만든 것을 지운다.

### 점유는 두 문장으로 나눈다. 원자성은 락이 지킨다

MySQL은 `update t ... where id in (select ... from t ...)`를 거절한다(ER 1093). 파생 테이블로 감싸면 통과하지만 materialize되어 `for update skip locked`의 잠금이 의미를 잃는다.

그래서 한 트랜잭션 안의 두 문장으로 바꾼다 — `select ... for update skip locked`로 **잠그며 고르고**, `update ... where id in (:ids)`로 새긴다. **나누어도 원자성은 그대로다.** 락이 커밋까지 유지되므로 두 문장 사이에 다른 인스턴스가 끼어들 수 없고, 그쪽의 `skip locked`가 잠긴 행을 건너뛴다.

문장 수는 여전히 인스턴스당 둘이므로 ADR-0011의 "N·M과 무관하게 두 문장"이라는 논거가 유지된다.

### 격리 수준은 점유 경로만 낮춘다

MySQL 기본값(REPEATABLE READ)에서 `for update` 범위 읽기는 갭 락까지 잡는다. 큐 테이블은 삽입이 계속 일어나므로 점유와 삽입이 교착한다. READ COMMITTED에는 갭 락이 없다.

**전역이 아니라 두 곳만 낮춘다** — `claimForDispatch`(notification)와 `claimForPublish`(order). 낮출 이유가 그 경로에만 있기 때문이다.

전역으로 낮추면 **애그리거트를 여러 테이블에서 읽는 조회들이 스냅샷 일관성을 잃는다.** 주문 조회가 `orders`와 `order_lines`를 한 트랜잭션의 두 문장으로 읽고, member·catalog·inventory·cart도 같은 모양이다. 지금은 자식 행이 같은 내용으로 다시 쓰이므로 무해하지만 그것은 현재 사실이지 구조가 보장하는 것이 아니다.

조건부 UPDATE로 점유하는 나머지 둘(`claimForPaymentReconciliation`, member의 발송 점유)은 기본 키 조회라 갭 락이 생기지 않으므로 손대지 않는다.

### 연결 시간대를 UTC로 고정한다

저장 타입이 `datetime(6)`이라 시간대를 담지 않는다. 그래서 **저장된 값의 해석이 연결 설정에 달린다.**

**일관되게 틀리는 것은 해가 없다.** 쓰기와 읽기가 같은 변환을 거치므로 왕복은 성립하고(member의 세션 만료), 점유의 시각 비교도 저장값과 비교값이 같은 변환을 거치므로 오프셋이 상쇄된다. 배타성이 깨진다고 적었던 것은 과장이었다.

고정하는 이유는 **어긋날 수 있는 경로를 없애기 위해서다.** 같은 데이터에 대해 설정이 시간에 걸쳐 바뀌면 예전에 쓴 값을 새 설정으로 읽게 되고, 인스턴스마다 설정이 다르면 한쪽이 쓴 것을 다른 쪽이 다르게 읽는다. 값 자체는 UTC가 아니어도 되지만 **모두가 같아야 하고**, 그러면 기준을 UTC로 두는 것이 가장 설명하기 쉽다.

### 이메일 컬럼에 대소문자 구분 콜레이션을 건다

MySQL 기본 콜레이션(`utf8mb4_0900_ai_ci`)은 대소문자를 무시한다. 유니크 인덱스만 걸면 `a@x.com`과 `A@x.com`이 같은 값으로 판정되어 [PD-0001](../policy/pd-0001-signup-and-email-verification.md)의 결정이 그대로 뒤집힌다.

**이 결함은 이번 전환이 없었으면 운영에서 발견됐을 것이다.** 정책은 문서에 있고 코드에는 유니크 인덱스만 있었으며, H2의 기본 비교가 우연히 대소문자를 구분했다. 검증되지 않은 경로가 무엇을 숨기는지의 실례다.

이메일에만 건다. 이름이나 주소까지 구분할 이유는 없다.

### 전체 검증은 작업이 끝나는 시점에 돈다

`make verify`는 도커를 요구하고 전부 돈다. pre-commit은 `@RequiresDatabase`가 붙은 것을 빼고 돈다.

**게이트를 둘로 나누는 것을 한 번 기각했었다.** CI가 없으므로 강제되지 않는 쪽이 방치된다는 이유였다. 여기서 성립하는 이유는 느린 쪽의 실행 시점이 **이미 절차가 강제하는 지점**이기 때문이다 — CLAUDE.md가 작업 완료 보고 전 실행을 요구하고, `rca-code-review`가 반영 후 검증을 돌린다. 관습이 아니라 워크플로에 걸려 있다.

커밋마다 MySQL을 띄우게 하면 커밋이 비싸지고, **비싼 게이트는 `--no-verify`로 우회된다.**

### 마이그레이션은 제자리에서 고친다

*"한 번 적용된 마이그레이션 파일은 고치지 않는다"* 의 예외다. H2 파일 DB를 전부 버리므로 `flyway_schema_history`를 이어받는 환경이 하나도 없다.

베이스라인 하나로 압축하지 않는다. 각 마이그레이션의 주석이 "왜 V2에서 이메일을 대소문자 구분으로 바꿨나" 같은 근거를 담고 있고 **그것이 정본이다.** 압축하면 그 근거가 사라진다.

## 고려한 선택지

### 테스트는 H2에 두고 운영만 MySQL — 채택하지 않음

하네스가 빠르고 도커가 필요 없다. 그러나 이것이 정확히 이 작업이 없애려는 상태다. 실제로 이번 전환에서 **H2가 숨기고 있던 결함이 둘 나왔다** — 이메일 대소문자와 `nulls first`. 대역에 두었으면 둘 다 운영에서 발견됐을 것이다.

### PostgreSQL — 채택하지 않음

점유의 핵심인 `for update skip locked`는 MySQL 8.0.1+와 PostgreSQL 9.5+ 둘 다 지원하므로 차이가 아니다. PostgreSQL이 유리한 지점이 둘 있다 — 자기 테이블 하위 질의 UPDATE를 받고, `timestamptz`가 있다. 둘 다 넘을 수 있는 수준이었고(두 문장으로 나누기, UTC 저장 규약), **넘을 수 있는 차이만 남으면 익숙함이 정당한 결정 요인이다.** 새벽에 락 대기를 들여다볼 사람이 익숙한 쪽을 쓰는 편이 낫다.

### 테스트마다 컨테이너 — 성립하지 않음

Testcontainers의 `jdbc:tc:` URL 스킴을 쓰면 문자열만 바꿔도 되지만 URL마다 컨테이너가 하나씩 뜬다. 38개다.

### 서비스마다 컨테이너 — 채택하지 않음

컨테이너 여덟 개가 뜬다. 격리는 데이터베이스가 만들므로 얻는 것이 없고, 개발자 머신에서 실질적으로 아프다.

### compose 경로를 자동으로 검증한다 — 하지 않음

백로그 목표에 있었으나, 그러려면 서비스 프로세스 열 개를 띄워야 하므로 e2e가 된다. 이 저장소는 그것을 만들지 않기로 했고 이번에 뒤집지 않는다. compose는 인프라를 포함하도록 고치되 실행은 수동 확인으로 둔다.

## 범위

**포함.** MySQL 8 도입과 여덟 서비스 설정. 마이그레이션 19개의 MySQL 문법 전환. 점유 SQL 두 곳을 두 문장으로. 점유 두 곳의 격리 수준. 테스트 지원 모듈과 38개 테스트 이전. compose에 MySQL. 하네스 분리와 문서.

**제외.** 카프카(BL-0055), 레디스, compose 자동 검증, 서비스 프로세스 e2e.

## 완료 기준

`make verify`가 MySQL 위에서 통과한다. 특히 `ClaimExclusivityTest`와 `OrderEventClaimExclusivityTest` — H2에서만 검증되던 것이 이 작업의 출발점이다. pre-commit이 도커 없이 통과한다.

## 결과와 제약

점유가 운영에서 쓸 DB 위에서 검증된다. H2가 숨기고 있던 결함 둘이 드러나 고쳐졌다.

대신 다음이 남는다.

- **`make verify`에 도커가 필요하다.** 컨테이너 재사용은 개발자 머신의 `~/.testcontainers.properties`에 opt-in이라 저장소가 강제할 수 없다.
- **하네스가 느려졌다.** 5초 안팎에서 25초 안팎으로 늘었다.
- **격리 수준 예외가 두 곳에 흩어져 있다.** 이유를 아는 사람만 유지할 수 있고, 새 점유 경로를 만드는 사람이 빠뜨릴 수 있다.
- **compose는 여전히 실행되지 않았다.** 인프라가 들어갔을 뿐 그것이 뜨는지는 확인되지 않았다.
- **컨테이너 재사용은 실측하지 못했다.** 개발자 홈의 `~/.testcontainers.properties`에 opt-in이라 저장소가 켤 수 없다. 재사용에서 깨지지 않는다는 근거는 `TestDatabaseTest`가 고정한 성질(같은 이름을 다시 요청해도 비어 있는 새 데이터베이스)뿐이다.

## 재검토 조건

- **카프카가 들어올 때** (BL-0055). 테스트가 브로커 컨테이너도 필요해지고, 컨테이너 수명과 격리 방식을 다시 본다.
- **새 점유 경로가 생길 때.** 격리 수준 예외를 빠뜨리면 조용히 교착하므로, 그때 예외를 흩뿌리는 대신 묶는 방법을 본다.
- **하네스 시간이 견디기 어려워질 때.** 컨텍스트당 데이터베이스를 줄이는 것이 첫 후보이며, 그때 테이블을 비우는 테스트들을 함께 고쳐야 한다.
- **DB를 다시 옮길 때.** 점유 SQL과 격리 수준 선택이 MySQL의 사정에서 나왔으므로 함께 움직인다.
