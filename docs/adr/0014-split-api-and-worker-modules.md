# ADR-0014: 실행 단위를 API와 워커로 나눈다

- **상태:** 승인됨
- **날짜:** 2026-08-30
- **해결한 백로그:** BL-0054 실행 모듈을 API와 워커로 나눈다
- **관련:** [ADR-0002](0002-network-segmentation-as-trust-boundary.md), [ADR-0003](0003-internal-path-prefix.md), [ADR-0012](0012-order-events-as-outbox.md), [ADR-0013](0013-real-database-in-the-harness.md)

## 맥락과 의도

서비스당 실행 가능한 서버가 하나다. `build.gradle`이 `apps/*` 전부에 boot 플러그인을 붙이는 것이 그 제약이며, 그래서 스케줄러가 API와 같은 프로세스에서 돈다.

**정확성 문제가 아니다.** 인스턴스가 여러 개여도 같은 작업을 두 번 하지 않는 것은 저장소의 점유가 보장하고, 그 성질은 실행 단위 구성과 무관하다. 문제는 구성이다.

**스케일 축이 어긋난다.** API 인스턴스 수는 요청 트래픽이 정하는데 워커 수가 그것을 따라간다. 처리량은 큐 깊이에 비례해야 할 값이다. 반대로 큐가 밀렸는데 트래픽이 적으면 워커만 늘릴 수 없다.

**자원이 격리되지 않는다.** 발송·발행은 외부 호출인데 사용자 요청을 처리하는 프로세스의 커넥션 풀과 스레드를 나눠 쓴다.

**그리고 카프카가 이 결정을 강제한다.** 아웃박스 릴레이가 프로듀서가 되고 notification이 컨슈머가 되는데([BL-0055](../backlog/done/bl-0055-publish-order-events-to-kafka.md)), 나누지 않으면 브로커 의존성이 API 모듈에 박힌다. **사용자 요청을 받는 프로세스가 브로커를 알아야 할 이유가 없다.** 뒤에 나누면 이미 박힌 의존성을 빼내는 일이 된다.

## 결정

### 서비스를 `core` · `api` · `worker` 셋으로 나눈다

```
apps/order-service/
  core/     domain, application, adapter/out/*      boot 플러그인 없음
  api/      adapter/in/web + 진입점                  bootJar
  worker/   adapter/in/scheduler + 진입점            bootJar
```

**절단면은 `adapter/in`이다.** 그리고 그것은 이 저장소가 이미 그어둔 선이다 — *"스케줄러나 앱 시작으로 구동되는 진입점은 `adapter/in` 아래 둔다. 컨트롤러와 역할이 같다"* (CLAUDE.md). 진입점을 한 자리에 모아둔 규칙이 그대로 실행 단위의 경계가 됐다. 새 경계를 발명한 것이 아니라 있던 경계를 빌드에 반영한 것이다.

나가는 어댑터(`adapter/out`)와 도메인·응용은 둘 다 쓰므로 `core`에 남는다.

**한 모듈에 진입점 둘을 두고 프로파일로 가르는 방법은 쓰지 않는다.** 배포 단위는 나뉘지만 **의존성이 같이 실린다.** 요구가 "API가 카프카를 몰라야 한다"이고 그것은 컴파일 시점의 문제이므로, 프로파일로는 만족시킬 수 없다. 무엇을 아는지를 런타임 설정이 아니라 클래스패스가 정하게 한다.

**`worker`가 `api`에 의존하는 두 모듈 구성도 쓰지 않는다.** 모듈이 하나 주는 대신 워커가 웹 코드를 끌고 간다. 나누는 이유의 절반이 사라진다.

### 공용 설정은 한 곳에 두고 가져온다

`core`에 공용 프로퍼티를 두고 `api`와 `worker`가 `spring.config.import`로 가져온다. 스프링은 클래스패스의 `application.properties`를 하나만 읽으므로 같은 이름을 두 모듈에 두면 하나가 조용히 이긴다.

복사하지 않는 이유는 **두 벌이 되면 반드시 어긋나기 때문이다.** DB 접속과 형제 서비스 URL이 그 대상이고, 어긋나면 API와 워커가 서로 다른 곳을 본다.

### 워커도 웹을 띄운다

`/actuator/health`를 노출한다. 웹 없이 띄우면 가볍지만 **살아 있는지 볼 방법이 없다.** 큐를 비우는 프로세스가 조용히 죽는 것은 이 저장소가 반복해서 문제 삼은 실패 모양이고, 기동 확인(`run-all.sh`)도 이 엔드포인트에 걸려 있다.

### Flyway는 API와 워커가 둘 다 돌린다

프로세스가 하나였을 때는 없던 상황이다. 한쪽만 돌리게 하면 소유자가 분명해지지만, **API만 돌리면 빈 DB에서 워커가 먼저 뜰 때 깨진다.** 그러면 기동 순서가 새 제약이 되고 배포가 그 순서를 지켜야 한다.

둘 다 돌리면 어느 것이 먼저 떠도 스키마가 준비된다. Flyway가 `flyway_schema_history`에 락을 걸어 동시 실행을 막으므로 안전하다.

**대가는 소유자가 없다는 것이다.** 워커만 배포해도 스키마가 바뀐다. 지금은 정확성 문제가 아니라 결정이 없는 상태이며, 실행 단위가 더 늘거나 마이그레이션 전용 단계를 만들 때 다시 본다.

### API는 기존 포트를 유지한다

형제 서비스의 `clients.*.url`이 바뀌지 않는다. 워커는 새 포트를 받는다.

### `core`는 자기 통합 테스트를 소유한다

`core`에는 boot 플러그인이 없어 `@SpringBootApplication`이 없고, 그래서 `@SpringBootTest`가 뜨지 않는다. **테스트 전용 부트 클래스를 `core/src/test`에 둔다.**

그 컨텍스트는 `core`의 빈만 스캔한다 — `api`와 `worker`가 클래스패스에 없기 때문이다. 그것이 원하는 바다. 저장소 어댑터와 변경 단위를 고립해서 검증한다.

밀어내는 대안은 배치를 설명할 수 없게 만든다. 사건 점유의 배타성 테스트가 웹 모듈에 있을 이유가 없다.

## 고려한 선택지

### 프로파일로 스케줄러를 켜고 끈다 — 채택하지 않음

가장 작다. `@Profile("worker")` 하나로 같은 jar을 두 역할로 띄운다.

그러나 의존성이 갈리지 않는다. 카프카 클라이언트가 API 프로세스의 클래스패스에 있고, 누가 API 코드에서 그것을 import해도 컴파일된다. **막으려는 것이 규율이 아니라 구조여야 한다면 프로파일로는 부족하다.**

### 서비스 전체를 나눈다 — 하지 않음

member의 인증 메일 발송기와 api-gateway의 프로브도 같은 모양이다. 그러나 이번에 나누는 근거는 카프카가 닿는 곳에서 의존성을 가르는 것이고, 그 둘은 카프카에 닿지 않는다. **필요 없는 곳에 실행 단위를 늘리면 배포 단위만 늘고 결정하는 것이 없다.**

이 결정이 그것을 가능하게 만들어 두므로, 필요해질 때 같은 모양으로 붙이면 된다.

## 범위

**포함.** order와 notification의 모듈 분리, 빌드 구성, 설정 분리, 테스트 배치, compose와 실행 스크립트, 문서.

**제외.** member·api-gateway의 분리, member의 external/internal 분리, 카프카(BL-0055).

## 완료 기준

`make verify` 통과. `make boot-all`로 12개가 뜨고 `make demo`가 끝까지 돈다.

**`api` 모듈의 컴파일 클래스패스에 워커 코드가 없다.** 카프카가 들어올 자리가 API에 없다는 것을 컴파일이 보장한다.

**워커가 죽어 있어도 API가 정상 응답하고, 워커만 띄우면 밀린 큐가 비워진다.** 스케일 축이 실제로 갈렸다는 증거다.

## 결과와 제약

API와 워커가 각자의 축으로 스케일된다. 워커의 배포·중지·튜닝이 API에 영향을 주지 않는다. 카프카가 들어올 때 브로커 의존성이 워커에만 붙는다.

대신 다음이 남는다.

- **배포 단위가 10개에서 12개가 된다.** 운영 대상이 늘고, 로컬 실행도 프로세스가 둘 더 뜬다.
- **테스트 컨텍스트가 늘어난다.** 모듈이 셋이면 각자 컨텍스트를 만들고 그만큼 데이터베이스가 더 생긴다. `make verify`가 느려진다.
- **운영에 없는 부트 클래스가 `core` 테스트에 하나 있다.** 그 컨텍스트와 실제 컨텍스트가 갈릴 수 있다.
- **두 서비스만 이 모양이다.** 나머지 여덟은 단일 모듈이라 저장소 안에 두 가지 구성이 공존한다.
- **나가는 어댑터는 나뉘지 않았다.** `core`가 HTTP 클라이언트 전부를 둘 다에게 주므로, 워커가 부르지도 않는 서비스의 URL 설정 없이는 뜨지 않는다. 실행 단위는 갈렸지만 협력자 의존은 그대로다 — 분리의 절반이며 [BL-0060](../backlog/done/bl-0060-move-outbound-adapters-to-their-units.md)에서 마저 한다. 카프카보다 앞에 두어야 한다.

## 재검토 조건

- **카프카가 들어올 때** (BL-0055). 이 분리가 실제로 의존성을 가두는지가 그때 증명된다. 못 가두면 절단면이 틀린 것이다.
- **세 번째 서비스를 나눌 때.** 지금은 두 사례라 공통 구성을 뽑지 않았다. 셋이 되면 빌드 구성을 공유할지 본다.
- **워커가 웹을 띄우는 비용이 문제가 될 때.** 헬스 확인 수단을 다른 것으로 바꿀 수 있다.
- **`core`의 테스트 컨텍스트가 실제와 갈려 문제를 놓칠 때.** 그때는 통합 테스트를 api·worker로 옮기는 쪽을 다시 본다.
