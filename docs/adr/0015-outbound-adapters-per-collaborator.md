# ADR-0015: 나가는 어댑터를 협력자별 모듈로 나눈다

- **상태:** 승인됨
- **날짜:** 2026-08-30
- **해결한 백로그:** BL-0060 나가는 어댑터가 쓰지 않는 실행 단위까지 따라간다
- **관련:** [ADR-0002](0002-network-segmentation-as-trust-boundary.md), [ADR-0014](0014-split-api-and-worker-modules.md)

## 맥락과 의도

[ADR-0014](0014-split-api-and-worker-modules.md)가 실행 단위를 API와 워커로 나눴지만 절단면이 `adapter/in`뿐이었다. **나가는 어댑터는 전부 `core`에 남아 둘 다에게 간다.**

order-service에서 실제 사용은 갈린다 — api는 협력자 여섯, 워커는 둘, 겹치는 것은 결제 하나다. 그런데 `CommerceRestClients`가 두 컨텍스트 모두에서 `RestClient` 빈 일곱을 만들고 URL 일곱을 요구한다. **워커는 부르지도 않는 다섯 서비스의 설정 없이는 뜨지 않는다.**

**어댑터만 옮겨서는 풀리지 않는다.** 응용 실행자도 `core`에 있고 컴포넌트 스캔이 그것을 두 컨텍스트 모두에서 집는다. `OrderExecutor`가 `core`에 남는 한 워커 컨텍스트가 `MemberClient` 빈을 요구한다. 워커가 클라이언트 일곱을 갖는 진짜 이유가 이것이다.

**그리고 카프카가 이것을 드러낸다.** [BL-0055](../backlog/bl-0055-publish-order-events-to-kafka.md)에서 워커의 발행 어댑터가 카프카로 바뀌어도 HTTP 클라이언트 다섯은 그대로 따라온다. "워커는 카프카만 알면 된다"가 성립하지 않는다.

## 결정

### 응용 컴포넌트와 그것이 쓰는 어댑터를 함께 옮긴다

옮기는 단위는 어댑터가 아니라 **"실행자와 그 협력자"** 다. `OrderExecutor`는 api로, 정리기와 발행기는 worker로 가고, 각자 쓰는 어댑터가 따라간다.

`core`에는 도메인·포트와 **둘 다 쓰는 응용 컴포넌트**(`OrderChanges`)만 남는다. 어댑터는 하나도 남지 않는다 — 남으면 "필요한 것만 의존한다"가 다시 깨진다.

저장소 어댑터는 둘 다 쓰므로 별도 모듈로 뺀다. `core`에 두면 위 규칙의 예외가 되고, 예외가 하나 생기면 다음 예외의 근거가 된다.

### 세 갈래로 묶는다

모듈이 여럿 생기므로 평평하게 두면 무엇이 무엇인지 보이지 않는다. `api`와 `client-cart`가 같은
층에 있으면 하나는 프로세스이고 하나는 클래스 하나짜리 어댑터인데 그 차이가 이름에만 있다.

```
apps/order-service/
  core/           바깥을 모른다 — 도메인, 포트, 둘 다 쓰는 응용
  infra/          바깥과 말한다 — persistence, client/*, publisher/*
  boot/           실행된다 — api, worker
```

세 묶음이 서로 다른 질문에 답한다 — 무엇이 배포되는가(`boot`), 이 서비스가 누구와 말하는가
(`infra`), 바깥을 모르는 것은 어디인가(`core`).

**`infra`는 나가는 어댑터다.** 들어오는 어댑터는 실행 단위와 1:1이라 그 안에 산다 — 컨트롤러는
API 프로세스의 얼굴이지 갈아끼울 대상이 아니다.

**발행 어댑터는 전송 수단으로 이름 짓는다.** `infra/publisher/http` 옆에 BL-0055가 `kafka`를
붙이고, 교체가 형제 사이의 교체로 보인다.

**좌표에 경로를 담는다.** 이름이 겹치면 Gradle이 두 프로젝트를 같은 모듈로 보고 하나를 다른
하나로 치환한다. `core`와 `notification`이 여러 자리에 나오므로 이름만으로는 구분되지 않으며,
실제로 발행 어댑터가 알림 클라이언트를 의존하는 것이 순환으로 잡혔다.

### 협력자마다 모듈을 만든다

클라이언트 하나가 모듈 하나다. 그것들이 공유하는 빌더 정책은 `client-core`에 둔다.

**이 모듈들이 만드는 경계는 "어느 실행 단위가 누구를 부를 수 있나"다.** 빌드 파일을 읽으면 그 답이 나오고, 부르지 않는 상대의 설정을 요구하지 않는다. [ADR-0002](0002-network-segmentation-as-trust-boundary.md)가 신뢰 경계를 네트워크 분리로 강제하기로 했는데, 그 경계가 처음으로 코드에 드러난다.

클래스 하나짜리 모듈이 여럿 생긴다. **크기가 아니라 경계가 기준이다** — 모듈이 작은 것은 협력자가 작기 때문이지 경계가 불필요해서가 아니다.

### 발행 어댑터도 모듈이다

`NotifyingOrderEventPublisher`는 클라이언트가 아니라 발행 포트의 구현이지만 같은 성질이다 — 워커만 쓰고, **BL-0055가 그것을 카프카로 갈아끼운다.** 모듈이면 그 교체가 의존 선언의 교체가 된다. 코드를 고치는 것이 아니라 무엇을 붙이느냐를 바꾸는 것이 되며, 그것이 ADR-0012에서 포트를 완성해둔 목적이다.

### `NotificationExecutor`를 수신과 발송으로 나눈다

한 클래스가 둘을 겸하고 생성자에 `MailSender`가 있다. **메일 어댑터를 워커로 옮기면 API 컨텍스트가 뜨지 않는다.**

메서드별 의존을 매핑하면 발송이 쓰는 넷(`MailSender`, 배치 크기, 재시도 간격, 최대 시도)을 다른 메서드가 하나도 쓰지 않는다. 겹치는 것은 저장소 하나다. `MemberService`를 셋으로 나눌 때와 같은 모양이며, 그때의 근거가 그대로 성립한다.

**여기서 새로 더해지는 힘은 실행 단위다.** 의존 집합이 겹쳐도 메서드가 서로 다른 프로세스에서 도는 것이 확정되면 그 클래스는 두 곳에 살 수 없다.

## 고려한 선택지

### `CommerceRestClients`를 실행 단위별로 셋으로 쪼갠다 — 채택하지 않음

모듈을 늘리지 않고 설정 클래스만 나눈다. 각 컨텍스트가 자기 것만 만든다.

그러나 **의존이 여전히 소스 배치에만 있다.** api 모듈에 워커용 클라이언트를 추가해도 컴파일된다. 막으려는 것이 "부르지 않는 상대를 알게 되는 것"이라면 그 경계는 빌드가 가져야 한다.

### 저장소 어댑터를 `core`에 남긴다 — 채택하지 않음

둘 다 쓰므로 core가 자연스러워 보인다. 그러나 그러면 core에 어댑터가 하나 남고, **"core에는 어댑터가 없다"는 규칙이 "겹치는 어댑터는 예외"로 약해진다.** 예외를 만들면 다음 어댑터도 "이것도 겹치니까"로 들어온다.

### 클라이언트를 서비스 간 공용 라이브러리로 뺀다 — 성립하지 않음

`HttpMemberClient`는 order-service의 `MemberClient` 포트를 구현한다. 포트는 그것을 요구하는 애플리케이션이 소유하므로, 공용으로 빼려면 포트도 공용이 되어야 하고 그러면 포트의 소유가 뒤집힌다.

## 범위

**포함.** order와 notification의 나가는 어댑터를 협력자별·실행 단위별 모듈로 분리. `NotificationExecutor` 분리. 응용 실행자를 쓰는 단위로 이동. 빌드 구성과 테스트 재배치.

**제외.** 카프카(BL-0055). member·api-gateway. 저장소 어댑터를 실행 단위별로 나누는 것.

## 완료 기준

`make verify` 통과. `make boot-all`로 12개가 뜨고 `make demo`가 끝까지 돈다.

**`order-worker`의 컴파일 클래스패스에 member·cart·catalog·inventory·shipping 클라이언트가 없다.** 그리고 워커 설정에서 그 다섯 URL을 지워도 기동한다 — 지금은 `@Value`가 요구해서 지울 수 없다.

## 결과와 제약

실행 단위가 부르는 상대가 빌드 파일에 드러난다. 부르지 않는 상대의 설정을 요구하지 않으므로 망을 나눠 배포할 때 코드가 그 경계를 지지한다. 카프카 교체가 의존 선언의 교체가 된다.

대신 다음이 남는다.

- **모듈이 여섯에서 열여덟으로 는다.** 대부분 클래스 하나짜리다. 세 갈래로 묶어 트리로는 읽히지만 수 자체는 그대로다.
- **`client-core`가 얇다.** 지금 공통은 "빌더를 한 번 주입받아 복제한다"는 규약뿐이다.
- **테스트 컨텍스트가 더 는다.** 모듈마다 컨텍스트와 데이터베이스가 생겨 하네스가 느려진다.
- **두 서비스만 이 모양이다.** 나머지 여덟은 단일 모듈이라 저장소 안에 세 가지 구성이 공존한다.

## 재검토 조건

- **카프카가 들어올 때** (BL-0055). 발행 어댑터 교체가 실제로 의존 선언만 바뀌는지가 이 결정을 검증한다.
- **세 번째 서비스를 나눌 때.** 모듈 구성을 공유할지 본다. 지금은 두 사례라 뽑지 않았다.
- **클래스 하나짜리 모듈이 유지에 부담이 될 때.** 협력자별 경계를 유지한 채 묶는 방법을 다시 본다.
- **협력자가 서비스 간에 재사용될 때.** 포트 소유를 다시 봐야 한다.

## 추가 결정

### 클라이언트 모듈은 테스트를 갖지 않는다

`infra/client/*`에 있던 테스트 둘을 지웠다. 컨텍스트를 띄우려면 가짜 부트 클래스가 필요했고,
그것이 `core`의 `@Component`를 피하려고 `scanBasePackages`로 스캔을 좁혀서 **운영과 다른
컨텍스트를 검증**하고 있었다.

대신 이것을 받아들인다 — `clients.http.read-timeout`이 실제로 적용되는지 재는 것과, 알림
어댑터가 실패를 삼키지 않는지 지키는 것이 하네스에서 사라진다. 두 성질 다 다른 테스트가
`NotificationClient`를 대역으로 바꿔 쓰므로 잡히지 않는다.

부수 효과로 두 모듈이 영속화 모듈 목록에서 빠졌다. 저장하는 것이 없는데 목록에 있던 이유는
테스트가 데이터베이스를 요구해서였고, 그대로 두면 클라이언트가 jdbc·flyway·mysql을 자기를
부르는 실행 단위로 끌고 간다. 이 작업이 없애려던 결합이다.
### 전송 수단으로 짓는 이름을 패키지와 클래스까지 적용한다

모듈만 `infra/publisher/http`로 짓고 나머지는 그대로 두었더니 이름이 셋으로 갈렸다 — 모듈은
전송 수단, 패키지는 `adapter.out.client`, 클래스는 대상(`NotifyingOrderEventPublisher`).

패키지를 `adapter.out.publisher`로, 클래스를 `HttpOrderEventPublisher`로 옮긴다. BL-0055가
`KafkaOrderEventPublisher`를 만들 때 그것이 `adapter.out.client`에 놓일 수는 없으므로 어차피
만들 자리다. 지금 만들면 카프카 커밋이 "옮기기"와 "추가"를 겸하지 않는다.

CLAUDE.md의 패키지 규칙에 `adapter/out/publisher`를 넣고 명명 근거를 한 줄로 남겼다.
