# ADR-0019: 공용 팩토리가 서비스 간 HTTP 클라이언트를 만든다

- **상태:** 승인됨
- **날짜:** 2026-09-14

## 맥락과 의도

Spring Boot의 `RestClient.Builder`는 주입 지점마다 새 인스턴스를 제공한다. 어댑터가 각자 빌더를
주입받으면 빌더 단위로 적용되는 타임아웃과 테스트 커스터마이저도 여러 갈래로 나뉜다. BL-0060에서
order-service의 클라이언트를 협력자별 모듈로 나눌 때 이 문제가 실제로 드러났고, 현재도 세 서비스가
빌더를 직접 주입받고 있다.

## 결정

`libs/common-http`가 프로세스에 하나인 `RestClientFactory`를 자동 구성한다. 팩토리는 모든
`RestClientCustomizer`를 순서대로 한 번 적용한 기준 빌더를 소유하고, 기준 URL마다 그 빌더를
복제해 클라이언트를 만든다. 어댑터는 팩토리와 기준 URL만 안다.

서비스 간 HTTP 호출이 있는 실행 단위는 Spring Boot의 `RestClientAutoConfiguration`을 제외한다.
따라서 `RestClient.Builder`를 직접 주입하는 코드는 기동하지 못하며, 공용 팩토리를 거치는 규칙이
구조로 강제된다.

## 고려한 선택지

팩토리만 제공하고 기본 빌더 빈을 남기는 방식은 채택하지 않는다. 기존 코드는 간단히 옮길 수 있지만
새 어댑터가 빌더를 직접 주입해도 아무 경고 없이 동작하므로 같은 문제가 다시 규율에 달린다.

서비스마다 클라이언트 수집자를 유지하는 방식도 채택하지 않는다. 공통 정책의 소유자는
`common-http`인데 서비스별 수집자가 같은 책임을 반복하고, 클라이언트 모듈을 나눌 때 다시
수집자 모듈에 의존하게 된다.

## 범위

- **포함:** 공용 팩토리 자동 구성, 기존 서비스 간 HTTP 클라이언트 생성 이전, 기본 빌더 자동 구성 제외,
  order-service의 수집자 모듈 제거
- **제외:** 클라이언트별 오류 변환과 상태 코드 정책, 서비스 간 API 변경

## 완료 기준

- 서비스 코드가 `RestClient.Builder`를 직접 주입하지 않는다.
- `CommerceRestClients`와 `GatewayRestClients`가 사라진다.
- 기존 컨텍스트·HTTP 스텁 테스트와 `make verify`가 통과한다.

## 위임된 결정

팩토리와 메서드 이름, 자동 구성 클래스 안에서의 빈 배치, 생성자 인자 배치는 기존 명명과 Spring
관례에 맞춘다.

## 결과와 제약

공통 타임아웃과 테스트 스텁이 모든 서비스 간 클라이언트에 같은 기준 빌더를 통해 적용된다.
Spring Boot가 기본 빌더 자동 구성에 새 기능을 추가하더라도 제외된 실행 단위에는 자동으로 들어오지
않으므로, 필요한 기능은 `common-http` 팩토리에 명시적으로 반영해야 한다.
