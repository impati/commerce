# ADR-0021: 서비스 간 호출 실패를 호출자 문맥으로 번역한다

- **상태:** 승인됨
- **날짜:** 2026-09-15

## 맥락과 의도

서비스 간 HTTP 호출에서 다운스트림 상태 코드를 그대로 올리면 그 상태가 호출자의 공개 계약인
것처럼 보인다. 그러나 같은 4xx라도 사용자가 고칠 수 있는 요청 거절과 서비스 사이의 잘못된 연동은
의미가 다르다. 연결 실패도 조회라면 안전하게 다시 시도할 수 있지만, 명령이라면 상대가 처리를
마쳤는지 알 수 없다.

각 클라이언트가 이 차이를 제각각 구현하면서 일부는 `RestClient` 예외를 그대로 노출하고, 일부는
다운스트림 오류 본문을 문자열로 검색하며, 같은 장애를 409·500·503으로 다르게 표현하고 있다.

## 결정

- 비게이트웨이 서비스 호출은 HTTP 예외를 그대로 올리지 않고 호출자 문맥의 `DomainException`으로
  번역한다.
- 호출자가 자신의 공개 계약으로 인정한 4xx만 호출자 문맥의 4xx로 번역한다. 예상하지 않은 4xx와
  응답 계약 불일치는 `downstream_error` 502로 번역한다.
- 조회의 다운스트림 5xx·연결 실패·시간 초과는 `service_unavailable` 503으로 번역한다.
- 부수효과가 가능한 명령의 다운스트림 5xx·연결 실패·시간 초과는, 처리가 끝났을 가능성을 버리지
  않도록 `outcome_unknown` 502로 번역한다. 조회와 명령은 HTTP 메서드가 아니라 호출 의미로 정한다.
- `libs/common-http`에 이 기본 번역을 수행하는 공통 실행 경계를 둔다. 각 어댑터는 호출을 조회나
  명령으로 선언하고 자신이 인정하는 4xx만 구조화된 `ErrorResponse.code`로 해석한다.
- 공통 경계 사용을 아키텍처 테스트나 전역 인터셉터로 강제하지 않는다. 명시적인 호출 코드와
  코드 리뷰로 적용하며, 예외적인 요구가 있는 어댑터가 별도 정책을 가질 여지를 남긴다.
- 공개 오류 메시지는 호출자가 소유한다. 다운스트림의 구조화된 코드와 메시지는 진단 로그에만
  남기며, 해석되지 않은 응답 본문 전체를 기록하지 않는다.
- API 게이트웨이는 의미를 번역하는 호출자가 아니라 프록시이므로 예외다. 다운스트림이 보낸 상태와
  응답 본문을 그대로 전달하는 현재 계약을 유지한다.

## 고려한 선택지

클라이언트마다 `try/catch`를 직접 두는 방식은 호출별 자유도가 높지만 이미 번역 누락과 의미 불일치를
만들었으므로 채택하지 않는다.

전역 인터셉터나 구조 검증으로 공통 정책을 강제하는 방식은 누락을 막지만 호출 문맥별 4xx 해석과
게이트웨이 예외를 숨긴다. 이번에는 선택적으로 호출하는 공통 실행 경계까지만 둔다.

다운스트림 상태와 메시지를 그대로 전파하는 방식은 프록시에는 맞지만 서비스 호출자에게는 내부
계약을 공개 API로 누출하므로 게이트웨이에만 허용한다.

## 범위

- **포함:** 공통 실행 경계와 오류 응답 해석, `downstream_error`, 비게이트웨이 HTTP 클라이언트
  이전, 오류 매핑 테스트
- **제외:** 재시도와 백오프 정책 변경, 게이트웨이 프록시 동작 변경, 저장된 실패 사유 타입화

## 완료 기준

- 비게이트웨이 HTTP 클라이언트에서 `RestClient` 예외가 응용 계층으로 새지 않는다.
- 예상한 4xx는 호출자 계약으로 번역되고, 예상하지 않은 4xx는 `downstream_error`가 된다.
- 조회와 명령의 다운스트림 장애가 각각 `service_unavailable`과 `outcome_unknown`으로 구분된다.
- 공통 경계와 주요 클라이언트 계약 테스트 및 `make verify`가 통과한다.

## 위임된 결정

공통 실행 경계의 클래스·메서드 이름과 제네릭 형태, 로그 형식, 테스트 배치는 저장소 관례에 맞춘다.

## 결과와 제약

호출자는 자신의 API 의미와 메시지를 소유하고, 공통 경계는 반복되는 프로토콜 판별을 한곳에서
관리한다. 사용을 기계적으로 강제하지 않으므로 새 클라이언트가 경계를 빠뜨릴 가능성은 남으며 코드
리뷰가 필요하다. 명령의 결과 불명은 자동 재시도 가능 여부를 뜻하지 않으며, 각 유스케이스가 조회나
멱등 키로 결과를 확인해야 한다.
