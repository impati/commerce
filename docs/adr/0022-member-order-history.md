# ADR-0022: 회원 주문 내역을 복합 커서와 고객용 조회 모델로 제공한다

- **상태:** 승인됨
- **날짜:** 2026-09-16

## 맥락과 의도

BL-0068은 회원이 접수한 주문을 목록에서 다시 찾고 상세에서 구매 내용과 진행 이력을 확인하게 한다. 고객 노출 기준은 PD-0020을 따른다. 같은 시각에 생성된 주문도 페이지를 넘길 때 중복되거나 누락되어서는 안 된다.

## 결정

- 주문 목록은 `created_at DESC, id DESC`로 정렬하고 두 값을 URL-safe Base64 커서에 함께 담는다. 모든 페이지 조건에 회원 식별자를 적용하며 커서는 권한으로 취급하지 않는다.
- 기본 페이지 크기는 20, 허용 범위는 1부터 100이다. 한 건을 더 조회해 다음 페이지 존재 여부를 판단한다.
- 기존 체크아웃 계약은 유지하고 주문 목록·상세는 별도의 고객용 조회 모델로 제공한다. 내부 결제·재고·발행 식별자와 오류는 고객 상세에 포함하지 않는다.
- 주문 조회는 주문·상품·체크아웃 진행을 일괄 읽고, 상세 타임라인은 주문 소유권 확인 뒤 기존 주문 사건을 발생 순서로 읽는다. 배송 서비스 장애와 무관하게 주문에 기록된 운송장과 사실을 보여준다.
- 주문 생성 시각과 사건 발생 시각은 UTC 기준의 불변 값이며 도메인 전이 시 주입된 시계로 결정한다. DB의 마이크로초 정밀도와 맞추고 API에는 UTC offset을 포함한다.
- `/orders`와 `/orders/{orderId}` 화면을 라우팅해 새로고침·직접 진입·뒤로가기를 지원하고, 인증 전에는 주문 데이터를 요청하지 않는다.

## 고려한 선택지

- 생성 시각만 커서로 사용하고 동률을 모두 응답하는 방법은 페이지 크기 초과에 상한이 없고 조회가 복잡해져 제외했다.
- 기존 체크아웃 응답을 내역에도 사용하는 방법은 내부 복구 정보가 고객 계약에 섞여 제외했다.
- 외부 결제·배송 서비스를 상세마다 다시 조회하는 방법은 이미 확정된 주문 사실이 외부 장애 때문에 보이지 않게 되어 제외했다.

## 범위

- **포함:** 주문·사건 시각, 복합 커서 조회, 소유권 검증, 고객용 목록·상세 API와 게이트웨이, storefront 화면, 관련 테스트.
- **제외:** 주문 취소 명령, 반품·환불, 상세 결제 거래, 운송사 배송 스캔, DLQ·운영 알림.

## 완료 기준

- 같은 생성 시각의 주문을 페이지 크기를 지키며 중복·누락 없이 조회한다.
- 정상 처리·보상 중·운영 확인·성공·실패를 PD-0020에 맞게 보여주고 타 회원 주문은 없는 주문과 동일하게 거절한다.
- 상품과 배송지 스냅샷 및 발생 시각이 있는 타임라인이 화면에 나타난다.
- `make verify`와 `make frontend-build`를 실행하고 결과를 보고한다.

## 위임된 결정

- DTO·컴포넌트 구조, 대표 상품 선택과 오류·로딩 표현은 기존 코드 경계를 지키며 정한다.
- 이미 작성 중인 BL-0068 변경은 같은 기능의 초안으로 이어받아 테스트와 함께 완성한다. 개인 설정은 제외한다.

## 결과와 제약

목록과 상세는 체크아웃 실행과 별개인 읽기 전용 유스케이스다. 커서와 시각은 저장 이후 변하지 않아야 한다. 로컬에서 기존 마이그레이션이 적용되었을 수 있으므로 새 마이그레이션으로 시각 제약과 색인을 추가한다. 고객 행동이 필요한 체크아웃이나 장시간 처리 안내를 도입할 때 조회 상태를 재검토한다.

## 추가 결정

- 주문 서비스의 유스케이스 입출력 타입과 페이지 위치 값은 `application.model`에 둔다. `port.in`에는 유스케이스 인터페이스만 남긴다. 조회 결과는 도메인 규칙을 책임지는 객체가 아니며, 커서는 입력·출력 포트가 함께 사용하므로 인바운드 전용 패키지에 속하지 않는다.
- 이 구조 변경은 주문 서비스에만 적용한다. 다른 서비스의 기존 입출력 타입 배치는 이번 BL-0068에서 변경하지 않는다. API·비즈니스 동작은 유지하고 참조와 기존 테스트를 함께 옮긴다.
