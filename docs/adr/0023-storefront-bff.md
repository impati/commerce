# ADR-0023: Storefront BFF가 화면 데이터를 조합한다

- **상태:** 승인됨
- **날짜:** 2026-09-16

## 맥락과 의도

Storefront가 여러 도메인의 데이터를 직접 조합하고 장바구니 합계를 계산한다. 지면 고도화에 따른 조합 책임을 게이트웨이나 도메인 서버에 누적하면 화면 변경과 업무 규칙 변경이 섞인다. BL-0082는 장바구니를 첫 대상으로 화면 조합의 오너십을 명시한다.

## 결정

- 독립 모듈과 프로세스인 Storefront BFF를 Gateway 뒤에 둔다. Gateway는 인증 검증과 라우팅을 유지한다.
- BFF는 화면 데이터를 조합하고 변경 명령을 도메인 서버에 위임한다. 장바구니는 Cart, 견적과 주문 금액은 Order가 소유한다.
- Order는 견적과 접수에 같은 가격 계산을 사용한다. 견적 식별값은 회원, 장바구니 버전과 서버가 계산한 구매 내용으로 만들고, 접수 때 다시 계산해 비교한다. 클라이언트의 금액을 신뢰하거나 견적을 예약으로 취급하지 않는다.
- 확인된 정보는 유지하고 조회 실패 영역을 표시한다. 금액과 재고를 확인하지 못하면 결제를 제한한다.
- 변경 성공과 후속 조회 실패를 구분한다. 결과 미확인은 재조회로 확인하고 담기 요청을 자동 반복하지 않는다.
- 다른 지면은 각 기능 작업 때 전환한다. 담당 팀, 배포 주기, 트래픽과 장애 격리 요구가 달라지면 BFF를 분리한다.

## 고려한 선택지

- 도메인 서버에 지면 전체를 맡기는 방법: 화면용 의존성과 배포 책임이 업무 서버에 누적되므로 제외했다.
- 지면마다 서버를 만드는 방법: 페이지 수보다 사용자 경험과 팀의 경계로 분리하기로 했다.
- Gateway에서 조합하는 방법: 화면 조합과 일부 실패 처리 책임은 BFF에 두기로 했다.

## 범위

- **포함:** BFF 도입, 장바구니 조회와 기존 담기, 서버 견적과 확인한 구매 내용의 주문 접수, 화면 및 로컬 실행 연결.
- **제외:** 다른 지면 전환, 쿠폰과 배송비 구현, BL-0069 수량 변경과 삭제.

## 완료 기준

정상 조회, 부분 실패, 변경 결과 미확인, 견적 및 장바구니 변경 거절, 멱등 재접수를 테스트한다. make verify, make frontend-test, make frontend-build가 통과한다.

## 위임된 결정

API와 DTO, 클래스 구성, 견적 식별과 검증, 조회 병렬화의 구현은 기존 포트·어댑터 규칙 안에서 판단한다.

## 결과와 제약

견적은 조회 시점의 값이며 주문 접수 때 재검증한다. 주문 접수 뒤의 구매 사본은 이후 장바구니나 상품 가격 변경에 영향을 받지 않는다. 기존 로컬 변경은 보존하고 이번 변경만 커밋한다.

## 추가 결정

- BFF의 조회와 변경 진입점은 입력 포트를 통해 응용 컴포넌트를 호출한다. 유스케이스는 자체 결과 타입을 반환하며, HTTP 응답과 접수 상태의 변환은 웹·클라이언트 어댑터가 맡는다.
- 부분 조회는 SKU별 결과와 실패 원인을 함께 보관한다. 화면 계약의 실패 영역 표시는 유지하며, 호출 실패와 견적 불일치를 내부에서 구분한다.
- 견적 확인을 생략하는 기존 구매 진입점은 제거한다. 실제 구매 경로의 검증을 위해 saga 테스트도 확인된 견적 경로를 사용한다. 테스트 유지 목적으로 운영 API를 남기지 않는다.
