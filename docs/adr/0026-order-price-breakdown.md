# ADR-0026: 주문이 금액 구성을 확정하고 모든 주문 화면에 제공한다

- **상태:** 승인됨
- **날짜:** 2026-09-19

## 맥락과 의도

주문 총액은 상품 라인 금액의 합만 나타내고 배송비가 없다. 고객은 결제 전에 최종 청구 금액의 구성을 확인할 수 없고, 주문도 배송비 정책이 바뀐 뒤 과거 금액을 그대로 설명할 값을 갖지 않는다. PD-0026으로 정한 상품 금액, 배송비와 최종 결제 금액을 견적부터 주문 내역까지 한 소유자가 일관되게 계산하고 보존해야 한다.

## 결정

- Order 도메인이 불변 `PriceBreakdown`을 소유한다. 상품 금액, 배송비와 최종 결제 금액을 함께 만들고 세 금액의 통화와 합계 불변식을 그 객체가 지킨다.
- 배송비 기준과 금액은 설정이 아니라 Order 도메인의 전용 정책으로 캡슐화한다. 정책 변경은 코드 리뷰와 배포를 거치며, 주문은 계산 규칙이 아니라 계산 결과를 저장한다.
- 견적과 주문 접수는 같은 가격 계산을 사용한다. 견적 식별에는 상품 내용과 확정 금액 구성이 반영되며, 접수 시 다시 계산한 구성이 다르면 새 견적 확인을 요구한다.
- 주문은 상품 라인의 단가뿐 아니라 상품 금액, 배송비와 최종 결제 금액을 함께 저장한다. 결제 승인에는 최종 결제 금액을 사용하며 이후 정책 변경으로 기존 주문을 다시 계산하지 않는다.
- Order 도메인 값과 서비스 간 응답 타입을 분리한다. 경계 매퍼가 `PriceBreakdown`을 응답으로 옮기고 BFF와 프론트엔드는 전달받은 값을 표시만 한다.
- 기존 API의 `total`은 최종 결제 금액으로 유지하고 `priceBreakdown`을 추가한다. 저장 상태는 하나이며 `total` 응답은 `PriceBreakdown`에서 파생한다.
- 장바구니, 결제 결과, 주문 목록과 주문 상세에 상품 금액, 배송비와 최종 결제 금액을 표시한다.
- `ORDER_CREATED` 사건은 기존 최종 금액을 유지하면서 상품 금액과 배송비를 추가한다. 적용한 정책 버전이나 계산 규칙은 싣지 않고 주문에 확정된 사실만 싣는다.
- 이미 적용된 Flyway 이력을 수정하지 않고 새 마이그레이션을 추가한다. 운영 주문 이력이 없는 기존 로컬 데모 행은 이전 청구 동작과 일치하게 배송비 0원으로 이관한다.

## 고려한 선택지

- 배송비 값을 실행 설정으로 관리하는 방안은 변경에 배포가 필요하다는 점이 코드 정책과 같으면서, 중요한 도메인 규칙이 설정 파일에 흩어져 제외했다.
- 유효기간별 정책을 DB에 저장하는 방안은 예약 변경과 운영 이력을 제공하지만 첫 도입에 관리 흐름과 동시 적용 규칙까지 요구해 제외했다.
- 공용 계약 타입을 Order 도메인에서 직접 사용하는 방안은 변환을 줄이지만 API 모양과 도메인 모델을 결합하므로 제외했다.
- 기존 `total`을 제거하는 방안은 응답을 단순하게 하지만 기존 호출자를 한 번에 깨뜨려 제외했다.
- 주문 생성 사건에 최종 금액만 유지하는 방안은 이후 소비자가 금액 구성을 알기 위해 Order를 다시 조회해야 하므로 제외했다.

## 범위

- **포함:** Order의 가격 정책과 금액 구성, 견적 검증, 주문 영속화와 결제 금액, HTTP 계약과 사건 계약, Storefront BFF, Gateway, 장바구니·결제 결과·주문 목록·주문 상세 화면, 관련 마이그레이션과 테스트.
- **제외:** 쿠폰·할인·세금, 지역·배송사·배송 속도별 요율, 다중 통화, 취소·반품·환불의 배송비 반환, 운영 중 동적 정책 변경과 관리 화면.

## 완료 기준

- 상품 금액 49,999원에는 배송비 3,000원, 50,000원에는 배송비 0원이 적용되고 비원화 견적과 주문은 거절된다.
- 견적 확인 뒤 상품 금액, 배송비 또는 최종 결제 금액이 달라지면 주문이 접수되지 않는다.
- 저장하고 다시 읽은 주문이 세 금액을 유지하며 결제 승인과 주문 생성 사건도 같은 구성을 사용한다.
- 장바구니, 결제 결과, 주문 목록과 주문 상세에서 세 금액을 확인할 수 있다.
- `make verify`, `make frontend-test`, `make frontend-build`가 통과한다. 새 핵심 테스트는 검증 대상 구현을 일부러 깨뜨렸을 때 실패하는지도 확인한다.

## 위임된 결정

클래스·메서드·DB 컬럼과 응답 필드의 세부 이름, 매퍼 배치, 0원 배송비 문구, 반응형 화면 배치, 오류 문구와 테스트 메서드 이름은 기존 저장소 규칙과 가독성을 따른다. 구현 커밋은 파일 종류가 아니라 독립적으로 리뷰할 수 있는 동작 단위로 나누며 최종 상태에서 전체 완료 기준을 검증한다.

## 결과와 제약

기존 `total`의 의미는 상품 금액에서 최종 결제 금액으로 확장되지만 필드 자체는 유지된다. 응답과 사건에 금액 구성이 추가되어 계약 크기는 늘어난다. 정책을 코드로 관리하므로 금액이나 기준 변경에는 배포가 필요하며, 대신 변경이 테스트와 코드 리뷰를 거친다. 백로그는 구현 검증 뒤에도 코드 리뷰가 끝날 때까지 열린 상태로 둔다.
