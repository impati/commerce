# ADR-0027: 고객 주문 취소를 별도 내구성 Saga로 실행한다

- **상태:** 승인됨
- **날짜:** 2026-09-19

## 맥락과 의도

성공한 주문에는 준비 중인 배송, 매입된 결제와 확정된 재고 예약이 있다. 고객 취소가 이들을 동기 HTTP 호출만으로 되돌리면 일부 호출 뒤 프로세스가 중단되거나 응답을 잃었을 때 어느 단계부터 다시 시작할지 알 수 없다. 체크아웃은 이미 저장된 진행 상태, 임차와 워커 복구로 같은 문제를 해결한다.

고객 취소도 출고와의 경합을 먼저 확정하고, 받아들인 요청은 전액 환불과 재고 복원을 거쳐 하나의 완료 결과로 끝나야 한다. 체크아웃 실패와 고객 취소는 서로 다른 사용자 사실로 남겨야 한다.

## 결정

- Order 서비스가 고객 취소를 조정한다. 배송 취소, 결제 환불과 재고 복원의 순서를 소유하고 각 협력 서비스는 자기 상태 전이를 멱등하게 제공한다.
- 완료된 체크아웃 진행을 다시 열지 않고 주문별 별도 취소 진행 상태를 저장한다. 취소 진행은 점유 임차, 지연 재시도와 운영 확인 상태를 가지며 API와 워커가 같은 실행기를 사용한다.
- 배송 취소를 첫 단계이자 취소 가능성의 경합 관문으로 둔다. 출고가 먼저 확정되면 취소를 거절하고, 배송 취소가 확정되면 환불과 재고 복원이 끝날 때까지 철회하지 않는다.
- 단계는 배송 취소, 결제 전액 환불, 확정 재고 복원, 주문 취소 확정 순서로 진행한다. 각 단계의 외부 결과를 저장한 뒤 다음 단계로 넘어가며, 응답을 잃으면 상태 조회로 결과를 판정한다.
- 재고 예약에는 확정 상태에서만 가능한 복원 전이를 추가한다. 복원은 예약 수량을 재고에 더하고 같은 요청에는 첫 결과를 반환한다. 범용 재고 이동 장부는 만들지 않는다.
- 한 주문의 취소 진행은 저장소 유일 제약으로 하나만 만든다. 별도 클라이언트 멱등 키 없이 주문 식별자를 취소의 업무 식별자로 사용한다.
- 고객 응답에는 체크아웃 결과와 분리된 취소 진행 상태를 제공한다. 목록과 상세는 처리 중, 확인 중, 완료를 표현하고 상세는 서버가 계산한 취소 가능 여부를 제공한다. 주문 도메인은 모든 되돌림이 끝난 뒤에만 `CANCELLED`가 된다.
- 주문 상세에서만 취소 동작을 제공한다. 자유 입력 사유 없이 전액 환불 안내를 확인한 뒤 요청하며, 처리 중에는 같은 동작을 비활성화하고 상태를 자동 갱신한다.
- 기존 체크아웃 실패 사건 `ORDER_CANCELLED`는 `CHECKOUT_FAILED`로 이름을 바꾼다. 고객 취소 접수는 `ORDER_CANCELLATION_REQUESTED`, 완료는 `ORDER_CANCELLED`로 기록하며 완료 사건만 취소 완료 알림을 만든다. 운영 데이터와 구버전 동시 배포가 없으므로 레거시 사건 호환 분기는 두지 않는다.
- 자동 판단이 위험한 상태는 내부적으로 운영 확인 대상으로 남기고 고객에게 취소 확인 중으로 표시한다. 성공이나 실패를 추정하지 않으며 안전한 재개 뒤 종단 상태에 도달한다.

## 고려한 선택지

- 체크아웃 진행 상태를 확장하는 방안은 저장 구조를 줄이지만 이미 완료된 구매 실행과 이후 고객 취소의 생애주기·재시도·고객 상태를 섞으므로 제외했다.
- 각 서비스가 취소 요청 사건에 반응하는 choreography는 직접 호출 결합을 줄이지만 배송 취소가 환불보다 먼저 확정되어야 하는 순서와 전체 완료 판정을 분산시키므로 제외했다.
- 전용 워크플로 엔진은 장기 실행과 운영 가시성이 좋지만 현재 취소 하나를 위해 새 인프라와 실행 모델을 도입하는 비용이 커 제외했다. 취소·반품·교환·정산 워크플로가 늘어나면 다시 검토한다.
- 주문을 요청 즉시 `CANCELLED`로 표시하는 방안은 응답이 빠르지만 돈과 재고가 아직 돌아오지 않은 상태를 완료로 보이게 하므로 제외했다.
- 범용 재고 추가 명령으로 수량을 돌리는 방안은 재시도 때 중복 증가를 막을 업무 식별자가 없어 제외했다.

## 범위

- **포함:** 고객 취소 정책, 취소 진행 영속화와 복구 워커, 배송 취소 경합, 결제 전액 환불, 확정 재고 복원, 주문 상태·사건·알림, Order API와 Gateway, 주문 목록·상세 상태와 상세 취소 UI, 관련 마이그레이션과 테스트.
- **제외:** 부분 취소·부분 환불, 출고 후 반품·교환, 자유 입력 취소 사유, 범용 재고 이동 이력, 전용 워크플로 엔진과 운영 관리 화면.

## 완료 기준

- 성공한 자기 주문의 배송이 준비 상태일 때만 취소가 받아들여지고, 출고와 취소가 겹치면 배송 저장소에서 먼저 확정된 전이만 성공한다.
- 상품 금액과 배송비를 합친 결제 전액이 한 번 환불되고, 확정된 모든 상품 수량이 판매 가능 재고로 한 번 복원된다.
- 각 단계 직후 실행을 중단해도 워커가 저장된 단계부터 재개하며, API와 워커 또는 반복 요청이 겹쳐도 효과가 중복되지 않는다.
- 외부 응답을 잃으면 상태 조회로 결과를 확인하고, 자동 판단이 위험하면 고객에게 확인 중으로 보이며 운영 신호가 남는다.
- 다른 회원, 성공하지 않은 체크아웃과 출고된 배송의 취소는 정해진 오류로 거절된다.
- 주문 목록과 상세에서 취소 진행 상태를 확인하고, 상세에서만 전액 환불 안내와 함께 취소할 수 있다.
- 체크아웃 실패, 고객 취소 요청과 고객 취소 완료가 서로 다른 진행 이력으로 나타나며 완료 알림은 한 번만 생성된다.
- `make verify`, `make frontend-test`, `make frontend-build`가 통과하고 핵심 테스트의 결함 감지력을 확인한다.

## 위임된 결정

진행 단계·테이블·API 응답 필드·오류 코드의 세부 이름, 임차·재시도 수치, 경계 매퍼 배치, 화면 문구와 반응형 배치, 테스트 클래스와 실패 주입 지점은 기존 체크아웃 구조와 저장소 관례를 따른다. 구현 커밋은 파일 종류가 아니라 독립적으로 리뷰 가능한 동작 단위로 나눈다.

## 결과와 제약

체크아웃과 같은 복구 모델을 재사용해 이해와 운영은 일관되지만 Order 서비스가 취소 단계의 순서와 여러 협력 서비스를 안다. 배송 취소가 확정된 뒤의 장애는 고객 취소를 되돌리는 대신 복구를 계속하므로 처리 중 또는 확인 중 상태가 길어질 수 있다. BL-0071에 의존하며, 재고 이동의 상세 감사 이력은 BL-0073에서 별도로 도입한다.

## 추가 결정

### 도메인과 유스케이스의 책임 경계

- 한 도메인 객체가 자기 상태와 명령 입력만으로 판단할 수 있는 불변식, 허용 상태 전이, 멱등 전이 결과와 사건 생성은 도메인 객체가 소유한다. 유스케이스가 상태 문자열이나 단계 enum을 비교해 같은 규칙을 다시 만들지 않는다.
- 도메인 내부의 유한한 상태는 enum으로 표현하고 DB와 HTTP의 문자열 표현은 영속화·응답 매퍼 경계에서 변환한다. 외부 계약을 도메인 모델의 편의를 위해 바꾸지 않는다.
- 유스케이스는 요청자 소유권 확인, 저장소 조회와 저장, 트랜잭션·행 잠금, 여러 aggregate와 외부 서비스의 실행 순서, 경합·임차·재시도를 조정한다. 이 작업은 한 도메인 객체가 혼자 판단하거나 수행할 수 없으므로 도메인 객체로 옮기지 않는다.
- 상태 전이가 멱등하면 도메인 메서드는 적용 여부를 명시적인 결과로 반환한다. 유스케이스는 그 결과를 사용해 재고 수량 같은 다른 aggregate의 효과를 한 번만 적용한다.
- 여러 도메인 객체의 사실을 결합한 안정적인 업무 규칙이 커지면 도메인 서비스로 분리한다. 현재 고객 취소는 각 객체의 작은 판단과 실행 순서 조정만으로 충분하므로 별도 자격 정책 서비스는 도입하지 않는다.
