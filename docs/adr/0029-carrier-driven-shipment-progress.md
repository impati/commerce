# ADR-0029: 택배사 사건을 배송 정본으로 삼아 주문에 투영한다

- **상태:** 승인됨
- **날짜:** 2026-09-24
- **해결한 백로그:** BL-0074 배송 진행을 운영자와 배송사 사건으로 갱신한다
- **관련 정책:** [PD-0025](../policy/pd-0025-carrier-driven-shipment-progress.md), [PD-0026](../policy/pd-0026-order-lifecycle-shipment-projection-and-price.md)

## 맥락과 의도

현재 배송은 생성과 동시에 내부 운송장을 발급하고 고객이 출고와 배송 완료를 직접 실행한다. Gateway는 배송 완료 직후 주문 완료까지 동기 호출하므로 배송과 주문이 독립적으로 다른 결과를 가질 수 있다. 이 구조는 운송장 발급과 실제 집하를 구분하지 못하고, 택배사가 보내는 중복·역순 사건과 최종 배송 실패·반송도 표현하지 못한다.

현재 사업 범위는 단일 판매자·단일 출고지·주문당 배송과 운송장 하나인 직매입 쇼핑몰이다. 실제 택배 업체는 연결하지 않되, 나중에 어댑터만 교체하면 실제 연동할 수 있어야 하며 택배사 구현의 성격이 배송과 주문의 핵심 로직에 퍼져서는 안 된다.

## 결정

- 물리적 배송 진행의 정본은 Shipping 서비스로 둔다. 주문은 배송이 확정한 공통 상태, 택배사, 운송장과 고객용 이력을 사건으로 받아 조회 투영을 유지한다.
- 배송은 택배사와 운송장 없이 `배송 준비 중`으로 만든다. 운영자가 포장 완료 내부 API를 호출하면 Shipping의 `CarrierGateway` 포트가 고정된 택배사에 접수하고, 접수가 확정된 뒤 운송장을 저장해 `집하 대기`로 전이한다. 배송 식별자를 업무 멱등 키로 사용한다.
- 운송장 발급과 출고를 분리한다. 출고는 택배사가 물건을 실제 인수한 집하 사건으로 확정하며, 집하와 고객 취소가 경합하면 Shipping 저장소에서 먼저 확정된 전이만 성공한다.
- 나가는 택배 접수·취소는 포트 뒤의 로컬 어댑터로 구현한다. 로컬 구현만 자신이 대역임을 알고, 핵심 로직과 계약은 실제 어댑터를 연결해도 바뀌지 않는다. 별도 택배사 시뮬레이터 서비스는 만들지 않는다.
- 외부 택배 웹훅은 유일한 공개 진입점인 API Gateway가 받는다. 택배사 전용 어댑터가 `eventId`, 전송 시각과 원문 본문의 HMAC 및 허용 시간 범위를 검증하고 택배사 고유 상태를 공통 사건으로 변환한 뒤 Shipping 내부 API로 전달한다.
- Shipping은 택배 사건 ID로 수신을 멱등하게 처리하고 원본 식별 정보, 발생 시각, 공통 사건과 처리 결과를 보존한다. 처리 결과는 `APPLIED`, `DUPLICATE`, `IGNORED_STALE`, `CONFLICT`를 구분한다. 늦은 사건은 현재 상태를 후퇴시키지 않고 서로 모순된 종결 사건은 기존 결과를 덮지 않는다.
- 택배사의 개별 배달 실패와 재시도는 내부 세부사항으로 보지 않는다. 최종 배송 불가 사건은 고객 이력에 실패를 남기고 배송을 `반송 중`으로 전이하며, 판매자 인수 사건은 `반송 완료`로 전이한다. 반송만으로 주문 취소·환불·재고 복원을 실행하지 않는다.
- Shipping 상태 전이와 Outbox를 한 트랜잭션에 기록하고 Kafka로 배송 사건을 발행한다. Order의 별도 `boot:consumer`가 사건 ID로 멱등하게 소비해 주문 배송 투영과 고객용 이력을 갱신한다. 배송 완료 사건만 주문을 배송 완료로 만들며 기존 배송 완료 알림을 한 번 발생시킨다.
- Shipping을 핵심 모듈과 영속화·택배사·Kafka 어댑터, `boot:api`, `boot:worker`로 분리한다. API는 운영 명령과 정규화된 택배 사건을 받고 Worker는 결과 불명 택배 접수 복구와 Outbox 발행을 담당한다. Order의 기존 API·Worker와 새 Consumer도 실행 단위별 의존성을 분리한다.
- 고객 주문 상세에는 마지막으로 확정된 공통 배송 상태, 택배사, 발급된 경우 운송장과 의미 있는 상태 변화만 표시한다. 택배 원본 코드, 중복·역순·충돌 기록과 서명 정보는 고객 이력에 포함하지 않는다.
- 고객이 호출하던 배송 출고·완료 API와 주문 직접 완료 API, Storefront의 `Ship`·`Deliver` 조작을 제거한다. 개발자는 별도 데모 스크립트로 운영자 포장 완료와 서명된 택배 웹훅을 재현한다.

## 고려한 선택지

- 주문 조회 때 Shipping을 동기 조회하면 투영 저장은 줄지만 Shipping 장애가 과거 주문 조회까지 막고 주문 완료와 고객 이력의 수렴도 보장하지 못해 제외했다.
- Gateway가 배송 완료 뒤 Order를 동기 호출하는 현재 흐름은 단순하지만 중간 실패와 재시도 때 두 서비스 상태가 갈라지므로 Outbox와 Kafka 사건으로 바꾼다.
- Order의 기존 Worker가 배송 사건도 소비하면 실행 단위는 줄지만 스케줄 복구와 브로커 소비의 역할·장애·확장 단위가 섞이므로 별도 Consumer를 둔다.
- Shipping API 프로세스가 Outbox를 발행하고 접수를 복구하면 배포 단위는 줄지만 요청 처리와 백그라운드 작업의 의존성 및 장애 범위가 섞이므로 Worker를 분리한다.
- 별도 택배사 시뮬레이터 서비스는 자동 상태 전이를 현실적으로 보일 수 있지만 새로운 상태·스케줄·운영 대상이 생겨 핵심 배송 흐름보다 범위가 커지므로 제외했다.
- 수신한 택배 사건을 그대로 고객 이력에 노출하면 구현은 단순하지만 중복·역순 사건과 택배사 코드가 고객 계약으로 새어 나가므로 원본 운영 기록과 고객용 투영을 분리한다.
- 기존 고객 상태 변경 API를 사용 중단 오류로 유지하면 호환성은 높지만 유지할 외부 클라이언트가 없고 우회 경로가 남으므로 완전히 제거한다.

## 범위

- **포함:** Shipping 모듈과 API·Worker 분리, 배송 상태와 사건 수신 이력, 택배 접수·취소 포트와 로컬 어댑터, 포장 완료 내부 API, Gateway HMAC 검증과 상태 정규화, Shipping Outbox와 Kafka 발행, Order Consumer와 배송 투영, 배송 완료 알림 연결, 고객 주문 API·화면, 직접 전이 경로 제거, 데모 스크립트와 관련 마이그레이션·테스트.
- **제외:** 실제 택배사·결제사·본인인증 업체 연동, 택배사 시뮬레이터 서비스, 어드민 화면·인증·권한·감사, 자체 배송, 다중 택배사 선택, 다중 판매자·분할 배송, 신규 상태별 고객 알림, 반송 뒤 검수·환불·재고 복원, 고객 구매 확정.

## 완료 기준

- 포장 완료와 접수 복구를 반복해도 배송별 운송장은 하나이며 운송장 발급만으로 고객 취소를 막지 않는다.
- 집하와 취소 경합에서 먼저 커밋한 전이만 성공하고 뒤의 요청은 물리적 사실을 덮지 않는다.
- 유효하지 않거나 허용 시간을 지난 서명 요청을 거절하며, 유효한 중복·역순·충돌 사건은 각각 정해진 처리 결과를 남기고 현재 상태를 중복 적용하거나 후퇴시키지 않는다.
- 최종 배송 불가와 판매자 인수가 반송 중·반송 완료로 나타나지만 환불·재고 복원·주문 취소를 자동 실행하지 않는다.
- Shipping 사건이 Order에 적어도 한 번 전달되어도 주문 투영과 고객 이력은 한 번만 바뀌며 배송 완료 알림도 한 번만 생성된다.
- 고객은 상태 변경 버튼 없이 주문 상세에서 배송 상태, 택배사, 운송장과 고객용 이력을 보고 개발자는 데모 스크립트로 전체 흐름을 재현한다.
- `make verify`, `make frontend-test`, `make frontend-build`가 통과하고 동시성·멱등성·역순·서명 거절의 결함 감지력을 확인한다.

## 위임된 결정

테이블·인덱스·Kafka 토픽·메시지 필드·API 오류 코드·클래스의 세부 이름, HMAC 알고리즘과 허용 시간, Worker 재시도 간격과 배치 크기, 기존 배송 데이터의 비파괴 호환 마이그레이션, 화면 문구와 테스트 배치는 기존 저장소 관례와 안전한 기본값을 따른다. 실제 업체명이나 대역임을 나타내는 코드가 핵심 계약에 고정되지 않도록 택배사 식별과 표시값은 어댑터가 제공하는 데이터로 취급한다.

## 결과와 제약

배송 사실의 소유자가 하나가 되고 주문 조회는 Shipping 장애 중에도 마지막으로 확정된 값을 제공한다. 반면 사건 전달 지연 동안 두 서비스의 표시가 일시적으로 다를 수 있고, 새 Consumer와 Worker를 각각 운영해야 한다. 실제 업체 연동 없이도 경계를 검증할 수 있지만 업체별 서명·접수 규격은 실제 어댑터를 추가할 때 구현해야 한다. 반송 이후 금전·재고 처리는 BL-0075, 운영 화면과 권한은 BL-0081, 자체 배송은 BL-0086, 다중 판매자 배송은 BL-0087에서 다룬다.
