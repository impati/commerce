# ADR-0030: 주문이 배송 후 반품 Saga를 내구성 있게 조정한다

- **상태:** 승인됨
- **날짜:** 2026-09-25
- **해결한 백로그:** BL-0075 배송 완료 주문의 반품과 환불을 처리한다
- **관련 정책:** [PD-0027](../policy/pd-0027-return-and-refund.md)

## 맥락과 의도

배송 후 반품은 고객 요청이나 배송 실패 반송에서 시작해 회수, 환불, 판매자 인수, 검수와 재고
판정을 거친다. 이 과정은 주문, 배송, 결제와 재고 서비스의 로컬 트랜잭션을 넘으며, 택배사와 결제
대행사 호출의 응답을 잃거나 어느 단계에서 프로세스가 종료될 수 있다. 동기 호출 순서만으로 연결하면
완료한 단계를 알 수 없어 환불과 재고 반영을 중복하거나 반품을 끝내지 못한다.

기존 원 배송은 배송 완료나 반송 완료로 물리적 결과가 확정된 종단 상태이고, 결제는 전액 환불만
표현하며, 재고는 판매 가능 수량과 예약 이동만 기록한다. 원 배송을 다시 열거나 현재 상태만 바꾸는
방식으로는 역배송과 금액 지정 환불, 판매 불가 반품을 설명할 수 없다.

## 결정

- Order 서비스가 주문별 반품 진행의 정본과 Saga를 소유한다. 고객 자격과 환불액을 확정하고,
  회수·환불·검수·재고 처리의 저장된 단계를 API와 Worker가 같은 실행기로 이어간다.
- 주문당 활성 반품은 하나이며 접수 때 만든 반품 식별자를 이후 회수·환불·재고 처리의 안정적인 업무
  멱등 키로 사용한다. 같은 요청의 반복은 기존 결과를 반환하고, 철회가 확정된 뒤 기간 안에 다시
  접수하면 새 반품 식별자를 만든다.
- Shipping 서비스는 원 배송과 분리된 역배송을 소유한다. 반품 식별자로 역배송을 하나 만들고 회수
  접수, 집하, 판매자 인수, 회수 실패와 철회를 기록한다. 배송 실패로 원 배송이 이미 반송 완료된
  경우에는 역배송을 만들지 않고 그 물리적 사실을 사용한다.
- 역배송 상태와 Outbox를 한 트랜잭션으로 커밋하고 사건을 적어도 한 번 전달한다. Order는 Inbox로
  중복을 제거하고, 철회와 집하 경합은 Shipping 저장소의 원자적 상태 전이에서 승자를 정한다.
- Payment 서비스는 반품 식별자와 환불 금액으로 금액 지정 환불 의도를 먼저 저장한다. PG 포트 호출은
  DB 트랜잭션 밖에서 수행하고 같은 키로 결과를 조회·재시도한 뒤 로컬 상태를 확정한다. 전액과 부분
  환불을 구분하되 기존 주문 취소와 체크아웃 보상의 전액 환불도 같은 내구성 경로를 사용한다.
- Inventory 서비스는 반품 식별자별 검수 결과를 멱등하게 적용한다. 판매 가능 결과는 현재 판매 가능
  수량과 이동 원장을 같은 트랜잭션으로 늘리고, 판매 불가·미검수 결과는 판매 가능 수량과 분리된
  격리 수량과 이력을 기록한다. 수동 검수와 72시간 만료가 경합하면 저장소 조건부 갱신의 첫 결과가
  이긴다.
- Order는 택배 집하가 확정되면 환불을 시작하고, 판매자 인수 뒤 검수·재고 처리와 환불 결과가 모두
  확정돼야 주문을 `반품 완료`로 전이한다. 각 외부 단계 직전의 의도와 직후 결과를 저장해 재시작 뒤
  완료한 단계부터 재개한다.
- 고객 요청은 공개 Gateway를 거치고, 검수 명령은 공개 Gateway에 노출하지 않는 내부 API로 둔다.
  운영 백오피스의 인증·권한과 화면은 이번 범위에 포함하지 않는다.
- 반품 사건은 기존 주문 Outbox와 알림 소비 경로를 사용한다. 고객에게 의미 있는 접수, 집하·환불
  시작, 완료와 운영 확인 상태만 알림으로 만들고 세부 복구 상태는 주문 상세 투영에만 둔다.

## 고려한 선택지

- 새 Return 서비스를 만들면 반품 경계는 독립되지만 주문당 전체 반품 하나를 위해 새 DB, 실행 단위,
  서비스 간 투영과 운영 대상을 추가해야 한다. 부분 반품과 교환 등 독립 생애주기가 늘어날 때 다시
  본다.
- 각 서비스가 사건에 자율 반응하는 choreography는 중앙 조정자를 없애지만 환불과 재고 처리 순서,
  전체 완료 판정과 결과 불명 복구 책임을 분산하므로 제외했다.
- 기존 원 배송을 반품에 재사용하면 레코드는 줄지만 서로 다른 운송장과 방향을 한 상태 기계에 섞고
  이미 확정된 종단 사실을 다시 열게 되므로 제외했다.
- 검수 뒤 환불하면 최종 사유를 금액에 반영할 수 있지만 PD-0027이 택배 집하 때 환불을 확정하므로
  제외했다.
- 환불 의도 없이 기존 동기 PG 호출을 재사용하면 부분 환불의 업무 키와 응답 유실 뒤 복구 근거가
  남지 않아 제외했다.

## 범위

- **포함:** Order 반품 진행과 복구 Worker, Shipping 역배송과 사건, Payment 금액 지정 내구성 환불,
  Inventory 판매 가능 복원과 판매 불가 격리, 주문 상태·이력·알림, 공개 고객 API와 화면, 내부 검수
  API, 데모 흐름, 마이그레이션과 관련 테스트.
- **제외:** 부분 반품·교환, 실제 택배사·PG 연동, 회원 구매·반품 제한, 판매 불가 상품의 재분류·판매,
  운영 백오피스와 범용 결제 거래 원장.

## 완료 기준

- 반품 자격, 환불 금액, 철회·재예약과 최종 주문 상태가 PD-0027과 일치한다.
- 외부 성공 뒤 응답 유실, 결과 저장 전 종료와 재시작에도 역배송과 환불은 같은 업무 키로 하나의
  결과에 수렴한다.
- API·Worker 동시 실행, 철회·집하 경합, 수동 검수·72시간 만료 경합과 같은 키의 동시 요청에서 효과가
  한 번만 적용된다.
- 중복·역순 역배송 사건이 현재 상태를 후퇴시키지 않고 Order 투영과 알림도 한 번만 바뀐다.
- 판매 가능 반품만 가용 재고를 늘리고 판매 불가·미검수 반품은 격리 수량과 이력으로 남는다.
- 주요 불변식 테스트를 의도적으로 깨뜨려 실패하는지 확인하고 원복한다.
- `make verify`, `make frontend-test`, `make frontend-build`와 `git diff --check`가 통과한다.

## 위임된 결정

테이블·인덱스·Kafka 토픽·메시지 필드·API 오류 코드·클래스의 세부 이름, 임차·재시도 간격과 배치
크기, 화면 문구와 반응형 배치, 테스트 배치는 기존 저장소 관례와 안전한 기본값을 따른다. 기간 경계는
한국 사업 기준인 `Asia/Seoul` 날짜로 판정하고, 실제 외부 업체가 없는 구현만 로컬 대역임을 안다.

## 결과와 제약

각 서비스가 자기 사실을 소유하면서 Order가 고객 반품의 완료를 한곳에서 판정하고, 중단 뒤에도
저장된 단계에서 복구할 수 있다. 대신 Order에 체크아웃·취소에 이어 반품 조정 책임이 추가되고,
Shipping과 Payment에 각각 새 내구성 작업이 생긴다. 고객 책임 훼손도 환불하는 비용과 판매 불가
재고의 후속 처리는 승인된 정책상 받아들인 제약이다.
