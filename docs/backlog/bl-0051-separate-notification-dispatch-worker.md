# 알림 발송이 API 프로세스 안에서 돈다

- **ID:** BL-0051
- **기록일:** 2026-08-29

## 배경

notification-service의 발송기([OutboxDispatcher](../../apps/notification-service/src/main/java/com/impati/commerce/notification/adapter/in/scheduler/OutboxDispatcher.java))가 API와 같은 프로세스에서 스케줄러로 돈다. 사용자 요청을 받는 실행 단위와 큐를 비우는 실행 단위가 하나로 묶여 있다.

**정확성 문제는 아니다.** 인스턴스가 여러 개여도 같은 알림이 두 번 나가지 않는 것은 [BL-0047](done/bl-0047-notification-dispatch-has-no-claim.md)이 저장소의 점유로 이미 보장했고, 그 성질은 실행 단위를 어떻게 구성하든 유지된다. 여기서 문제 삼는 것은 구성이다.

**스케일 축이 어긋난다.** API 인스턴스 수는 요청 트래픽이 정하는데 발송기 수가 그것을 따라간다. 발송 처리량은 큐 깊이에 비례해야 할 값이다. API를 늘리면 폴러가 같이 늘어 매 주기 같은 큐 머리를 두고 점유를 경쟁한다. `skip locked`라 안전하지만 스캔과 락 시도는 낭비이고, 반대로 큐가 밀렸는데 API 트래픽이 적으면 발송기를 따로 늘릴 수 없다.

**자원이 격리되지 않는다.** 발송은 외부 호출(수락 조회 + 전송, 최악 건당 8초)인데 사용자 요청을 처리하는 프로세스의 커넥션 풀과 스레드를 나눠 쓴다. [BL-0004](done/bl-0004-member-service-outbox.md)가 끊은 것은 "벤더 상태가 가입 트랜잭션에 들어오는" 결합이고, 발송기가 API 프로세스에 사는 한 벤더가 느릴 때 그 부하가 API 프로세스 안에서 발생하는 더 약한 결합이 남는다.

**운영 독립성이 없다.** 발송만 멈추거나, 발송 설정만 바꾸거나, 발송기만 배포할 수 없다. API 재배포가 진행 중인 발송을 끊는다 (임차가 자기치유하므로 유실은 아니다).

같은 모양이 세 곳 더 있다 — member-service의 인증 메일 아웃박스, order-service의 결제 정리, api-gateway의 프로브. 이 항목은 발송량이 실재하는 notification부터 다루되, 결정이 나머지에도 적용될 모양인지 함께 본다.

두 결정이 이 항목에 선행하거나 함께 간다. 실행 단위를 나눌 수 있는지는 [BL-0012](bl-0012-split-runtime-modules.md)가 이미 잡아둔 빌드 구성의 결정이다. 브로커 기반 컨슈머로 가는 선택지는 [ADR-0010](../adr/0010-verification-mail-outbox.md)이 "브로커는 아웃박스의 대안이 아니라 뒤에 오는 것"으로 방향을 잡아뒀다 — 아웃박스는 그대로 두고 발송 전달만 갈아끼운다.

## 목표

알림 발송이 API와 독립된 실행 단위에서 돌고, 각자의 축으로 스케일된다. API 인스턴스 수는 요청 트래픽이, 발송 워커 수는 큐 깊이가 정한다. 발송기의 배포·중지·튜닝이 API에 영향을 주지 않는다.

어떤 방식으로 나눌지는 이 항목을 시작할 때 정한다. 어느 쪽이든 점유와 수락 확인이 만든 성질(배타성·백오프·중복 방지)은 실행 단위 구성과 무관하게 유지되어야 한다.
