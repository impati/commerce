# 체크아웃이 중단되면 진행 상태를 잃어 복구하지 못한다

- **ID:** BL-0057
- **기록일:** 2026-08-29

## 배경

[OrderExecutor.checkout](../../apps/order-service/boot/api/src/main/java/com/impati/commerce/order/application/component/OrderExecutor.java)은 재고 예약, 결제 승인, 배송 생성, 매입을 외부 서비스에 요청하고 주문에 결과를 저장한다. 외부 처리와 주문 저장은 하나의 트랜잭션이 아니므로, 외부에서는 성공했지만 주문에는 결과가 남지 않은 채 중단될 수 있다.

원래 이 항목은 매입 성공 후 주문 확정 저장이 실패하는 구간을 다뤘다. 이때 결제는 매입됐지만 주문은 `CREATED`로 남고, `payment_outcome_unknown`도 표시되지 않아 기존 결제 정리기의 대상에서 빠진다.

같은 공백이 현재 체크아웃의 다른 단계에도 있다. 재고 예약·결제 승인 후 결과 저장 전에 종료되면 주문에 상대 식별자가 남지 않을 수 있고, 생성된 배송 정보는 매입 후 주문 확정 전까지 메모리에만 있다. 외부 호출의 응답을 받지 못한 경우에도 실제 처리 여부를 확인해야 한다. 성공 응답 뒤에 결과를 저장하는 것만으로는 이 공백을 없애지 못한다.

매입 전 예외는 보상을 시도하지만, 프로세스가 종료되면 보상 코드가 실행되지 않는다. 보상 자체도 실패하거나 도중에 중단될 수 있다. 현재 코드는 보상 실패를 원래 예외에 붙이고 나머지 보상을 계속하므로 원인 유실 문제는 일부 해결됐지만, 미완료 보상을 재시작 후 찾아 끝낼 근거는 부족하다.

매입 후에도 남은 작업이 있다. 재고 예약 확정에 실패하면 예약은 유지되어 가용 수량은 맞지만 보유 수량이 실물과 어긋난다. 이를 방치된 예약으로 보고 해제하면 이미 팔린 재고가 다시 팔릴 수 있다. 장바구니 비움도 실패하거나 실행 전에 중단될 수 있으며, 나중에 다시 처리할 때 고객이 새로 담은 상품을 지우지 않아야 한다.

2026-09-10 사용자 합의로 BL-0057의 범위를 체크아웃 중단 복구 전체로 확장하고, **BL-0033(보상 실패 시 원인 보존과 미완료 보상 복구)** 및 **BL-0038(매입 후 미확정 재고 예약 복구)**의 목표를 흡수한다. 2026-09-11에는 체크아웃 응답 유실과 중복 접수를 같은 복구 흐름에서 다루기로 하면서 **BL-0035(체크아웃 요청 멱등성)**도 흡수했다. 이번 통합은 사용자가 승인한 예외로 BL-0057 ID를 유지하며, 세 항목은 완료 처리하지 않고 이 항목으로 대체한다. 삭제한 ID는 재사용하지 않는다.

## 목표

체크아웃이 중단돼도 진행 상황과 외부 처리 결과를 확인하고, 재개 또는 보상하여 끝낼 수 있다. 현재 호출 경로의 외부 처리 성공 후 저장 실패, 응답 유실, 프로세스 종료와 보상 도중 중단을 다룬다.

매입이 확인된 주문은 취소로 되돌리지 않고 주문 확정을 이어서 완료한다. 매입 전 단계의 재개·보상 기준과 결과를 확인할 수 없는 경우의 처리는 인터뷰에서 정한다.

보상이 실패해도 원래 체크아웃 실패 원인을 보존하고, 미완료 보상을 찾아 마무리할 수 있다. 매입된 주문의 미확정 재고 예약은 찾아서 확정하며, 방치된 예약과 구분해 이미 팔린 재고를 해제하지 않는다. 예약 만료 자체는 [BL-0025](bl-0025-inventory-reservation-never-expires.md)에 남긴다.

매입 후 재고 확정과 장바구니 처리까지 완료 여부와 안전한 후속 처리 기준을 다룬다. 중단 후 재개나 반복 실행이 중복 외부 처리, 중복 사건 또는 고객이 새로 담은 상품의 삭제로 이어지지 않아야 한다.

같은 체크아웃 요청이 여러 번 도착하거나 최초 응답이 유실돼도 주문과 결제는 한 벌만 만들어지고, 기존 처리 상태와 서버가 발급한 주문 식별자를 다시 얻을 수 있다. 클라이언트가 만든 멱등 키는 인증된 회원 안에서 체크아웃 접수와 결과 확인에만 사용하며, 주문 식별자나 다른 시스템의 업무 식별자를 대신하지 않는다. 완료·실패 후에도 키 매핑을 보존하고 같은 키에 다른 구매 내용이 오면 거절한다.

진행 상태의 저장 방식, 단계별 재개·보상 기준, 원래 요청과 복구의 동시 실행 방지, 재시도와 관측 방법은 인터뷰에서 정한다. 범용 워크플로 엔진 도입을 전제로 삼지 않는다.
