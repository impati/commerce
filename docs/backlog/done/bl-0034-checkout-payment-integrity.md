# 체크아웃에서 결제와 재고가 어긋난 채 남는다

- **ID:** BL-0034
- **기록일:** 2026-08-22
- **대체:** BL-0024(예약 확정 후 실패하면 재고와 결제가 새어나간다), BL-0027(결제 요청이 멱등하지 않다)

## 배경

원인이 둘로 보이지만 하나다. 결제가 **첫 호출에서 즉시 매입**되고([PD-0008-R1](../../policy/pd-0008-payment-capture.md)), 그 매입이 **주문 성립보다 앞서** 일어난다([PD-0004-R5](../../policy/pd-0004-checkout-and-compensation.md)).

**재고와 결제가 새어나간다.** 체크아웃은 재고 예약, 결제 확정, 예약 확정, 배송 생성 순으로 진행한다. 예약이 확정되기 전에 실패하면 예약을 풀고 주문을 취소하지만, 확정된 뒤에 실패하면 아무것도 되돌리지 않는다([PD-0004-R7](../../policy/pd-0004-checkout-and-compensation.md)). 그 결과 재고는 차감되고 결제는 승인된 채로 주문만 취소된 상태가 만들어진다. 사용자는 돈을 냈는데 주문은 취소로 보이고, 재고는 아무에게도 팔리지 않은 채 줄어 있다. 확정된 결제를 취소할 수단이 아예 없으므로([PD-0008-R4](../../policy/pd-0008-payment-capture.md)) 되돌리려 해도 되돌릴 수 없다.

**같은 주문이 여러 번 결제된다.** 같은 주문으로 결제를 여러 번 요청하면 그때마다 새 결제가 확정된다([PD-0008-R5](../../policy/pd-0008-payment-capture.md)). 이전 요청과 같은 요청인지 확인하지 않고, `payments` 테이블에도 `order_id` unique 제약이 없어 어느 층에도 방어가 없다. 체크아웃 호출에는 읽기 타임아웃이 걸려 있으므로 결제 서비스가 느리면 호출자는 실패로 판단하고 상대는 결제를 확정한 상태가 된다. 사용자가 다시 시도하면 결제가 두 건 만들어지고, 실제 결제 대행사를 붙이면 이 지점이 곧 이중 청구가 된다.

되돌리기를 의도적으로 포기한 것인지 검토되지 않은 구간인지는 기록에 없다.

## 목표

체크아웃이 어떤 지점에서 실패해도 재고와 결제가 서로 어긋난 채 남지 않는다. 자동으로 되돌릴 수 없는 구간이 남는다면 그 구간이 무엇이고 왜 되돌리지 않는지가 정책으로 드러나 있다.

같은 요청이 여러 번 도착해도 결제는 한 번만 확정된다. 무엇을 같은 요청으로 볼 것인지의 기준이 정해져 있다.

규칙이 바뀌므로 [PD-0004](../../policy/pd-0004-checkout-and-compensation.md), [PD-0008](../../policy/pd-0008-payment-capture.md), [PD-0010](../../policy/pd-0010-shipment-progress.md)을 수정하지 않고 새 정책 문서로 대체한다.
