# 실행 모듈을 API와 워커로 나눈다

- **ID:** BL-0054
- **기록일:** 2026-08-29

## 배경

지금은 서비스당 실행 가능한 서버가 하나여서 컨슈머·배치·internal API를 따로 만들 수 없다. `build.gradle`이 `apps/*` 전부에 boot 플러그인을 붙이는 것이 코드적 제약이다.

그래서 스케줄러가 API와 같은 프로세스에서 돈다. 네 서비스가 그렇다 — notification의 발송기, member의 인증 메일 발송기, order의 결제 정리, api-gateway의 프로브.

**정확성 문제가 아니다.** 인스턴스가 여러 개여도 같은 작업을 두 번 하지 않는 것은 저장소의 점유가 이미 보장했고([BL-0047](bl-0047-notification-dispatch-has-no-claim.md)), 그 성질은 실행 단위를 어떻게 구성하든 유지된다. 문제 삼는 것은 구성이다.

**스케일 축이 어긋난다.** API 인스턴스 수는 요청 트래픽이 정하는데 워커 수가 그것을 따라간다. 처리량은 큐 깊이에 비례해야 할 값이다. API를 늘리면 폴러가 같이 늘어 매 주기 같은 큐 머리를 두고 점유를 경쟁한다. `skip locked`라 안전하지만 스캔과 락 시도는 낭비이고, 반대로 큐가 밀렸는데 API 트래픽이 적으면 워커만 늘릴 수 없다.

**자원이 격리되지 않는다.** 발송은 외부 호출인데 사용자 요청을 처리하는 프로세스의 커넥션 풀과 스레드를 나눠 쓴다. [BL-0004](bl-0004-member-service-outbox.md)가 끊은 것은 벤더 상태가 가입 트랜잭션에 들어오는 결합이고, 워커가 API 프로세스에 사는 한 벤더가 느릴 때 그 부하가 API 프로세스 안에서 발생하는 더 약한 결합이 남는다.

**운영 독립성이 없다.** 워커만 멈추거나, 설정만 바꾸거나, 워커만 배포할 수 없다. API 재배포가 진행 중인 작업을 끊는다(임차가 자기치유하므로 유실은 아니다).

**그리고 카프카가 이 결정을 강제한다.** 아웃박스 릴레이가 카프카 프로듀서가 되고 notification이 컨슈머가 되는데([BL-0055](bl-0055-publish-order-events-to-kafka.md)), 나누지 않으면 브로커 의존성이 API 모듈에 박힌다. 사용자 요청을 받는 프로세스가 브로커를 알아야 할 이유가 없다. 분리가 카프카보다 앞이어야 하는 이유가 이것이다 — 뒤에 하면 이미 박힌 의존성을 빼내는 일이 된다.

이 항목은 BL-0012(실행 단위를 나눌 수 있는가)와 BL-0051(알림 발송을 API에서 분리)을 대체한다. 앞의 것은 빌드 구성의 결정이고 뒤의 것은 그 첫 적용 대상이었는데, 카프카가 들어오면서 둘이 한 작업이 됐다.

## 목표

한 서비스가 여러 실행 단위를 가질 수 있고, API와 워커가 각자의 축으로 스케일된다. API 인스턴스 수는 요청 트래픽이, 워커 수는 큐 깊이가 정한다. 워커의 배포·중지·튜닝이 API에 영향을 주지 않는다.

**대상은 order와 notification 둘이다.** 카프카에 닿는 최소 집합이다. member의 인증 메일 발송기와 api-gateway의 프로브는 성격이 달라 필요할 때 따로 본다 — 이 항목이 그것을 가능하게 만들지만 이번에 하지는 않는다. BL-0012가 언급한 member의 external/internal 분리도 같다.

어느 쪽이든 점유가 만든 성질(배타성·백오프·중복 방지)은 실행 단위 구성과 무관하게 유지되어야 한다. 그 성질이 스케줄러가 아니라 저장소에 있다는 것이 지금까지의 설계이며, 이 작업이 그것을 검증한다.
