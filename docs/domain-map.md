# Domain Map

## 식별한 도메인

사용자가 상품을 보고 결제와 배송 완료까지 가는 데 필요한 도메인은 다음과 같이 식별했습니다.

| 도메인 | 포함한 이유 | 핵심 모델 |
| --- | --- | --- |
| 회원 | 주문 주체와 배송지 소유 | `Member`, `Address` |
| 전시 | 사용자가 상품을 발견하는 화면 구성 | `DisplaySection` |
| 상품 | 판매 대상과 가격 스냅샷 | `Product`, `Sku` |
| 재고 | 한정 자원 보호, 예약/확정/해제 | `StockItem`, `Reservation` |
| 장바구니 | 주문 전 구매 의도 | `Cart`, `CartLine` |
| 주문 | 상거래 트랜잭션의 중심 aggregate | `Order`, `OrderLine` |
| 결제 | 외부 PG와 유사한 승인/매입 경계 | `Payment` |
| 배송 | fulfillment lifecycle | `Shipment` |
| 알림 | 고객/운영자 커뮤니케이션 | `Notification` |
| API Gateway | 외부 인증 검증과 라우팅 | route, downstream client |
| Storefront BFF | 화면 데이터 조합과 도메인 명령 위임 | 장바구니 화면 응답 |

## 선택한 분리 기준

1. 데이터 소유권이 다르면 서비스를 나눴습니다.
2. 변경 속도가 다른 영역을 분리했습니다. 예를 들어 전시 정책은 주문 정책보다 자주 바뀝니다.
3. 장애 격리와 보상 트랜잭션이 필요한 영역을 명시했습니다. 결제 실패는 재고 예약 해제와 주문 취소로 보상됩니다.
4. 조회 중심 도메인인 전시/상품과 트랜잭션 중심 도메인인 주문/재고/결제를 분리했습니다.

## 응집 단위 — 함께 지켜져야 하는 것

위의 표는 **서비스 사이**의 경계다. 이 절은 그 안쪽 — 한 트랜잭션 안에서 정합성이 지켜져야 하는 단위다.

**불변식이 걸리는 범위가 애그리거트 경계다.** 한 번에 지켜야 하는 규칙이 두 객체에 걸치면 그 둘은 하나의 애그리거트이고, 나누면 규칙을 지킬 주체가 사라진다.

| 애그리거트 | 함께 지켜야 하는 불변식 | 쪼개면 무엇이 깨지나 |
| --- | --- | --- |
| `Member` + `Address` | 기본 배송지는 정확히 하나 | 새 기본 배송지를 넣을 때 기존 것을 내릴 주체가 없어져 기본이 둘이 된다 |
| `Order` + `OrderLine` | `total`은 라인의 합이고, 상태 전이는 정해진 순서를 따른다 | 라인만 따로 바꾸면 total과 어긋난다. 결제된 주문의 라인이 바뀔 수 있다 |
| `Cart` + `CartLine` | 같은 SKU는 한 줄이며 수량이 합산된다 | 같은 SKU가 여러 줄로 들어가고 주문 라인이 중복된다 |
| `StockItem` | `reserved`는 `onHand`를 넘지 않는다 | 초과 예약. 재고 없는 주문이 결제된다 |
| `EmailVerification` | 단일 사용이며 만료가 있다 | 토큰 재사용 |
| `Session` | 폐기되거나 만료되면 쓸 수 없다 | 로그아웃이 반영되지 않는다 |

지키는 방법은 넷이다.

1. **루트를 통해서만 바꾼다.** 내부 컬렉션은 복사해서 내준다 (`List.copyOf`). 원본을 내주면 밖에서 수정해 불변식을 우회한다.
2. **저장은 애그리거트 단위로 원자적이어야 한다.** 루트를 저장하면 자식이 같은 트랜잭션에서 함께 쓰인다.
3. **애그리거트 사이는 식별자로 참조한다.** 서비스 경계를 넘는 것은 HTTP라 이미 강제되지만, 같은 서비스 안에서도 지킨다.
4. **동시성 아래에서는 코드만으로 부족하다.** `StockItem`은 `select for update`와 check 제약으로 DB에서도 지킨다. 애플리케이션 검사만 두면 두 트랜잭션이 동시에 통과한다.

### SRP와 충돌하지 않는다

층위가 다르다. **SRP는 응용 계층에 적용되고, 응집은 도메인 애그리거트에 적용된다.** member-service의 응용 서비스를 셋으로 나눌 때 `Member` 애그리거트는 한 줄도 나누지 않았다.

실은 같은 규칙이다. SRP는 "바뀌는 이유"로 나누는 것이고, **하나의 불변식을 지키는 코드는 같은 이유로 바뀐다.** 충돌해 보이면 둘 중 하나를 잘못 적용한 것이다.

불변식을 지키는 단위를 쪼개면 결과는 anemic domain이다 — 데이터만 있는 객체와, 그 데이터의 규칙을 밖에서 대신 검사하는 서비스가 생긴다. 그러면 검사를 빠뜨린 경로가 규칙을 깬다. 규칙을 한 곳에서만 지킬 수 있게 두는 것이 목적이다.

## 현재 구현의 현실적인 단순화

- 저장소가 있는 8개 서비스는 MySQL을 쓰고 스키마는 Flyway로 관리합니다. 운영 인스턴스는 붙이지 않았습니다.
- 주문 사건은 아웃박스에서 Kafka로 발행하고 notification-consumer가 구독합니다.
- 서비스 디스커버리는 쓰지 않고 설정값의 base URL로 연결합니다.
- 운영 환경에서는 각 서비스별 DB, broker, tracing, retry, circuit breaker를 추가하는 것이 다음 단계입니다.
