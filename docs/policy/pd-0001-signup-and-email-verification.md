# PD-0001: 가입과 이메일 소유 확인

- **날짜:** 2026-08-17

> 이 문서는 이미 구현되어 있던 규칙을 코드에서 읽어 옮긴 것이다. 규칙은 코드에서 확인한 사실이고, 근거는 주석이나 기존 문서에 기록이 남아 있는 것만 적었다. 기록이 없으면 `근거 미기록`으로 둔다 — 추정으로 채우면 이 결정을 뒤집을 때 근거로 쓸 수 없다.

## 배경과 문제

이 정책은 **누가 계정을 가질 수 있고, 그 계정이 언제부터 사용 가능해지는가**에 답한다.

이메일은 계정의 식별자이면서 동시에 유일한 연락 수단이다. 소유가 확인되지 않은 주소로 계정이 활성화되면 남의 주소로 계정을 만들 수 있고, 이후의 주문 알림과 계정 복구가 엉뚱한 사람에게 도달한다. 반대로 확인 절차를 과하게 두면 가입 자체가 끊긴다. 이 정책은 그 경계를 정한다.

정책 문서가 없을 때 이 규칙들은 코드 여러 곳에 흩어져 있었고 전모를 담은 기록이 없었다. 규칙 하나를 바꿀 때 나머지와 충돌하는지 확인할 방법이 없는 상태였다.

## 목표

**계정의 식별자가 되는 이메일 주소는 그것을 실제로 받아볼 수 있는 사람만 사용할 수 있다.** 소유가 확인되기 전의 계정은 존재하되 아무 권한도 갖지 않으며, 확인 절차는 사용자가 외부 도움 없이 스스로 복구할 수 있을 만큼 관대하다. 확인 수단이 되는 토큰은 계정을 활성화할 자격이므로 비밀번호와 같은 급으로 다룬다.

## 정책

- **PD-0001-R1:** 가입이 완료된 계정은 이메일 소유가 확인되기 전까지 미인증 상태이며, 로그인할 수 없다. 근거 미기록.
- **PD-0001-R2:** 이미 같은 이메일로 가입된 계정이 있으면 가입 요청을 거절한다. 근거 미기록.
- **PD-0001-R3:** 이메일의 유일성은 대소문자를 구분해 판정한다. 근거: 두 주소가 같은 사서함인지는 수신 도메인이 정하는 것이므로 발신 측에서 단정하지 않는다. 중복 계정이 생길 위험은 소유 확인으로 막는다고 보았다.
- **PD-0001-R4:** 비밀번호는 8자 이상이어야 한다. 상한과 문자 구성 요구는 두지 않는다. 근거 미기록.
- **PD-0001-R5:** 이메일 주소는 `@`를 포함해야 한다. 그 밖의 형식은 검사하지 않는다. 근거 미기록.
- **PD-0001-R6:** 이메일 소유 확인 토큰은 한 번만 사용할 수 있고, 발급 후 24시간이 지나면 만료된다. 근거 미기록.
- **PD-0001-R7:** 이미 사용된 토큰과 만료된 토큰은 구분하지 않고 같은 응답으로 거절한다. 근거: 어느 쪽인지 알려주면 유효한 토큰이 존재했다는 사실이 드러난다.
- **PD-0001-R8:** 확인 메일을 재발송해도 이전에 발급된 토큰은 무효화되지 않는다. 발급된 토큰은 각자 만료 시각까지 유효하다. 근거 미기록.
- **PD-0001-R9:** 확인 메일의 발송 요청이 실패해도 가입은 유지된다. 근거: 메일 시스템 장애로 가입을 막을 이유가 없고, 사용자는 재발송으로 복구할 수 있다.
- **PD-0001-R10:** 이미 소유 확인을 마친 계정의 재발송 요청은 거절한다. 근거 미기록.

## 거절하는 시나리오

- 대문자가 섞인 주소로 가입한 사용자가 전부 소문자로 로그인을 시도하면 실패한다. 두 주소는 서로 다른 계정으로 취급된다 (R3).
- 소유 확인을 마치지 않은 사용자가 로그인하면 거절된다. 비밀번호가 맞아도 마찬가지다 (R1).
- 한 번 사용한 확인 링크를 다시 누르면 거절된다 (R6).
- 발급 후 24시간이 지난 확인 링크는 거절된다 (R6).
- 이미 확인을 마친 사용자가 확인 메일 재발송을 요청하면 거절된다 (R10).
- 8자 미만의 비밀번호로는 가입할 수 없다 (R4).
- `@`가 없는 문자열은 이메일로 받지 않는다 (R5).

## 허용하는 시나리오

- 대소문자만 다른 두 주소로 각각 계정을 만들 수 있다. 같은 사람이 같은 메일함으로 두 계정을 갖는 상태가 성립한다 (R3).
- 확인 메일이 실제로 발송되지 않아도 계정은 만들어진 상태로 남는다. 사용자는 재발송으로 복구한다 (R9).
- 확인 메일을 여러 번 재발송하면 유효한 토큰이 동시에 여러 개 존재한다. 그중 어느 것을 써도 확인된다 (R8).
- 길이 제한이나 문자 구성 요구가 없으므로 매우 길거나 단순한 비밀번호도 받아들인다 (R4).
- 존재하지 않는 이메일 주소로도 가입할 수 있다. 형식만 통과하면 계정은 만들어지고, 확인 메일이 도달하지 않아 미인증 상태로 남는다 (R5, R1).

## 정책이 정하지 않는 것

- 비밀번호를 어떤 방식으로 해싱해 저장하는가.
- 확인 토큰을 어떻게 생성하고 어떤 형태로 보관하는가.
- 확인 메일의 문구, 발송 수단, 발송 시점.
- 가입과 재발송 요청의 빈도 제한.
- 로그인 세션의 수명과 폐기 방식. 별도 정책의 대상이다.
- 미인증 상태로 남은 계정을 언제까지 보관하는가.

## 고려한 대안

**R3의 대안 — 이메일을 소문자로 접어 비교한다.** 채택하지 않았다. 대소문자가 다른 두 주소가 같은 사서함인지는 수신 도메인이 결정하며, 접어버리면 실제로 구분되는 사서함의 주인이 가입할 수 없게 된다.

나머지 규칙은 기록 없음. 이 문서는 이미 구현된 규칙을 옮긴 것이며 당시 검토한 대안이 남아 있지 않다. 이후 규칙을 바꿀 때는 그 시점의 대안과 버린 이유를 새 문서에 남긴다.

## 재검토 조건

아래 조건은 이 문서를 작성하면서 정한 것이며, 원래 결정 시점의 판단이 아니다.

- 소셜 로그인이나 이메일 외의 가입 수단을 도입할 때. 이메일이 유일한 식별자라는 전제가 깨진다.
- 대소문자만 다른 중복 계정이 실제로 관측될 때 (R3).
- 가입 전환율에서 소유 확인 단계의 이탈이 문제로 보고될 때 (R1).
- 계정 열거나 확인 토큰을 이용한 공격이 관측될 때 (R2, R7).

## 미결

없음. 이 문서는 결정을 새로 하지 않고 현행 규칙을 기록한 것이다. 바꾸어야 한다고 판단한 규칙은 미결로 두지 않고 별도 작업 항목으로 분리했으며, 그 작업이 규칙을 바꾸면 이 문서를 고치지 않고 새 정책 문서로 대체한다.
