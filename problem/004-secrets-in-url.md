# URL에 비밀을 담으면 어디로 새는가

작성일 2026-08-23 / 관련 백로그 BL-0002 / 관련 결정 [ADR-0006](../docs/adr/0006-verification-token-in-url-fragment.md)

## 배경

이메일 확인 링크가 토큰을 쿼리스트링에 담고 있었다.

```
http://localhost:5173/verify?token=a3f9c2d4e8b1...
```

백로그 항목([BL-0002](../docs/backlog/done/bl-0002-verification-token-referer-leak.md))은 이것을 **Referer 유출** 문제로 기록했고, 대응으로 `Referrer-Policy: no-referrer` 헤더를 먼저 넣고 프래그먼트 전환은 나중에 판단하자고 적어 두었다.

조사해 보니 **그 순서가 뒤집혀 있었다.** 헤더가 막으려던 경로는 이미 브라우저 기본값이 막고 있었고, 정작 막히지 않는 경로를 헤더가 못 막는다. 이 문서는 그 확인 과정과, "URL에 비밀을 담는다"는 것이 실제로 무엇을 의미하는지를 남긴다.

## 문제의 뿌리

**URL은 비밀을 담는 그릇으로 설계된 적이 없다.**

URL은 목적지를 나타내는 주소다. 그래서 웹 인프라 전체가 URL을 **기록하고, 복사하고, 다른 데로 보내는 것을 기본 동작으로 삼는다.** HTTP 요청 본문이나 헤더에는 그런 관성이 없다.

이 하나의 사실에서 유출 경로 셋이 갈라져 나온다.

## 경로 A — 웹 서버 접근 로그

브라우저가 `GET /verify?token=a3f9c2...`를 보내면 **그 요청이 지나가는 모든 서버가 URL 전체를 로그에 쓴다.** nginx 기본 로그 포맷이 그렇고 CDN·로드밸런서·WAF도 같다. 설정 실수가 아니라 기본 동작이다.

```
192.0.2.10 - - [23/Aug/2026:10:14:22] "GET /verify?token=a3f9c2d4e8b1... HTTP/1.1" 200
```

무게는 셋에서 온다.

**로그가 토큰보다 오래 산다.** 토큰 수명은 24시간이고([PD-0001-R6](../docs/policy/pd-0001-signup-and-email-verification.md)) 접근 로그 보관은 통상 수 주에서 수 년이다.

**로그 접근 권한이 DB 접근 권한보다 넓다.** 수집기로 흘러가고 백업되고 장애 분석 때 덤프로 공유된다.

**토큰이 소진되지 않은 채 로그에 남는 경우가 흔하다.** 이게 가장 반직관적인 부분이다. "일회용이니까 로그에 찍힐 때쯤엔 이미 써버린 것 아닌가"가 자연스러운 반문인데, 소진하는 것은 GET이 아니라 **그 뒤에 JS가 보내는 POST**다. 둘 사이가 벌어지는 경우가 흔하다.

| 상황 | 로그에 남나 | 토큰이 소진되나 |
| --- | --- | --- |
| 정상 클릭 | ○ | ○ (수백 ms 뒤) |
| 메일 보안 스캐너·링크 미리보기 | ○ | ✗ — **JS를 실행하지 않는다** |
| JS 로드 실패, 즉시 탭 닫기 | ○ | ✗ |
| API 호출 실패 | ○ | ✗ |

아래 세 줄에서 토큰은 로그에 평문으로 남은 채 만료까지 유효하다. 그리고 링크 스캐너(Outlook Safe Links, Slack 언펄)는 기업 메일 환경의 예외가 아니라 기본이다.

## 경로 B — Referer 헤더

브라우저는 어떤 페이지에서 나가는 요청에 "나 이 페이지에서 왔다"는 `Referer`를 붙인다. **링크 클릭뿐 아니라 이미지·스크립트·폰트 로드에도 붙는다.**

이 저장소에서 실제로 성립한다. [App.tsx](../frontend/storefront/src/App.tsx)가 상품 이미지를 `images.unsplash.com`에서 가져오고, SPA라서 `/verify` 경로로 들어와도 같은 컴포넌트가 그린다.

```
GET /photo-1521572163474-... HTTP/1.1
Host: images.unsplash.com
Referer: http://localhost:5173/verify?token=a3f9c2d4e8b1...
```

우리 토큰이 **우리가 지울 수도, 조회할 수도, 보관 기간을 알 수도 없는 남의 로그**에 들어간다.

### 그런데 이 경로는 이미 막혀 있었다

브라우저에는 `Referrer-Policy`가 있고 이것이 Referer에 URL을 얼마나 담을지 정한다. **기본값이 바뀌었다.**

| 정책 | 크로스오리진 요청에 담기는 것 |
| --- | --- |
| `no-referrer-when-downgrade` (**옛 기본값**) | URL 전체 — 토큰 포함 |
| `strict-origin-when-cross-origin` (**현재 기본값**, Chrome 85 / Firefox 87) | 오리진만 — `http://localhost:5173/` |
| `no-referrer` | 아무것도 안 보냄 |

즉 백로그가 "먼저 막자"고 한 대상은 **우리가 아무것도 하지 않아도 이미 막혀 있었다.** 헤더를 넣는 것의 실제 가치는 "지금 새는 것을 막는다"가 아니라 "**나중에 다시 새지 않게 못 박는다**"였다 — CDN이 정책을 느슨한 값으로 덮어쓰거나 개별 요소에 `referrerpolicy="unsafe-url"`이 붙으면 조용히 되살아나기 때문이다.

## 경로 C — 브라우저 이력과 사람의 복사

URL은 주소창에 뜨고 방문 이력에 들어간다. 코드가 `history.replaceState`로 지우지만 **JS가 실행되고 API 응답을 기다린 뒤에야** 돌아간다. 그 전에 이미 이력·세션 복원·브라우저 동기화에 들어갔을 수 있고, JS가 실패하면 아예 안 지워진다.

그리고 사용자는 "이거 왜 안 돼요?" 하며 주소창을 복사해 채팅에 붙여넣는다. URL은 사람들이 아무 경계심 없이 복사하는 물건이다.

## 앞뒤가 맞지 않던 지점

[RegistrationExecutor](../apps/member-service/src/main/java/com/impati/commerce/member/application/component/RegistrationExecutor.java)는 DB에 토큰 원본이 아니라 해시를 저장한다.

```java
emailVerificationRepository.save(new EmailVerification(
        secureTokens.hash(rawToken),   // 원본이 아니라 해시
        ...
```

비밀번호를 다루는 방식이다. **이 코드는 이미 "이 토큰은 DB가 통째로 유출돼도 쓸 수 없어야 하는 비밀"이라고 판단하고 있었다.** 그렇게 감춘 원본이 접근 로그에는 평문으로 박혔다. 금고를 잠그고 열쇠를 현관 방명록에 적어 둔 셈이다.

**저장 시점의 판단과 전달 시점의 판단이 어긋나 있었다는 것**이 이 문제의 실체다. 유출 경로 셋은 그 어긋남이 밖으로 드러난 형태다.

## 피해 크기 — 과장하지 않기

지금 이 토큰이 하는 일은 `member.activate()` 하나다. 세션을 주지 않으므로 유출돼도 계정 탈취가 되지 않는다.

성립하는 시나리오는 계정 선점이다. 공격자가 `victim@example.com`으로 가입하고(비밀번호는 공격자가 정함) 인증 메일은 피해자에게 간다. 피해자가 무시하면 정상적으로는 그 계정이 영영 활성화되지 않는데, 로그에서 토큰을 읽으면 **피해자의 이메일 주소를 단 계정을 활성화**할 수 있다.

**고쳐야 하는 진짜 이유는 다른 데 있다.** `/verify?token=`이라는 형태는 다음에 **비밀번호 재설정이나 매직 링크가 놓일 자리**다. 그때 같은 경로는 계정 완전 탈취가 된다. 지금 바로잡는 비용은 파일 두 개, 나중에 바로잡는 비용은 이미 발송된 링크와 축적된 로그 전부다.

## 조치

토큰을 URL 프래그먼트로 옮겼다.

```
http://localhost:5173/verify?token=a3f9c2...   서버가 본다. 로그에 남는다
http://localhost:5173/verify#token=a3f9c2...   서버는 "/verify"만 본다
```

프래그먼트는 **브라우저가 서버로 전송하지 않는다.** 문서 내 위치를 가리키는 것이라 서버가 알 필요가 없고, 규격상 요청 라인에 포함되지 않는다. 같은 이유로 Referer에서도 제거된다. 즉 **경로 A와 B가 한 번에 닫힌다.**

`Referrer-Policy` 헤더는 병행하지 않았다. 프래그먼트에 있는 토큰은 애초에 Referer에 실리지 않으므로 헤더가 추가로 막는 것이 없다. 다만 "브라우저 기본값은 보장이 아니다"는 위험이 남으므로, 정적 호스트 설정이 저장소에 생기는 시점을 ADR-0006의 재검토 조건으로 남겼다.

경로 C는 닫지 않았다. 프래그먼트도 주소창에 뜨고 이력에 들어간다. 세션을 발급하는 토큰을 링크로 보내게 될 때 다시 볼 일이다.

## 하네스의 사각지대

**링크 형식을 고정하는 테스트가 하나도 없었다.** `#`를 `?`로 되돌려도 `make verify`가 통과했다. 즉 이 수정을 유지하는 장치가 문서 말고는 없는 상태였다.

[problem/001](001-read-triggers-write.md)·[problem/002](002-positional-jdbc-binding.md)와 같은 계열이다. 세 번 다 **초록불이 무언가를 보증한다고 믿었는데 그 무언가가 검증 대상에 들어 있지 않았다.** 001은 인메모리 대역이 검증 대상과 같은 가정을 공유했고, 002는 왕복 테스트가 대칭 오류를 상쇄했고, 여기서는 아예 단언이 없었다.

`VerificationLinkTest`를 추가하면서 단언을 짝으로 뒀다. 프래그먼트를 요구하는 것과 쿼리스트링을 금지하는 것이다. 앞만 있으면 링크가 하나 더 붙는 식으로 쿼리 경로가 되살아나도 걸리지 않는다.

`#`를 `?`로 되돌려 두 테스트가 실제로 실패하는 것을 확인하고 원복했다. 통과만 확인한 테스트는 통과만 하는 테스트일 수 있다.

## 배운 것

**"이 경로가 실재한다"와 "이 경로가 지금 새고 있다"는 다르다.** 백로그가 지목한 unsplash Referer 경로는 실재했지만 브라우저 기본값이 막고 있었다. 대응을 정하기 전에 **어느 것이 실제로 열려 있는지**를 확인해야 순서가 뒤집히지 않는다. 확인하지 않았다면 헤더 한 줄을 넣고 "BL-0002 완료"로 닫았을 것이고, 가장 무거운 경로가 그대로 남았을 것이다.

**기본값에 기대는 보호는 보호의 부재와 다르지만 보장과도 다르다.** 브라우저 기본 정책은 우리가 통제하지 않는다. 이번에는 프래그먼트가 그 위험까지 함께 없앴지만, 그렇지 않은 상황에서는 명시하는 쪽을 골라야 한다.

**한 시스템 안에서 같은 값을 다른 무게로 다루고 있으면 그 자체가 신호다.** DB에는 해시를, 로그에는 평문을 남기고 있었다. 어느 쪽이 맞는지는 더 엄격한 쪽이 답이다 — 느슨한 쪽에 맞춰 내리는 것이 아니라.
