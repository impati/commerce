# URL에 비밀을 담으면 어디로 새는가

작성일 2026-08-23 / 관련 백로그 BL-0002 / 관련 결정 [ADR-0006](../docs/adr/0006-verification-token-in-url-fragment.md)

## 이메일 소유 확인이 하는 일

회원가입에서 이메일 소유 확인은 "이 주소가 정말 당신 것인가"를 묻는 절차다. 방법은 대체로 같다. **아무나 추측할 수 없는 문자열을 하나 만들어 그 주소로만 보내고, 그걸 되가져오면 소유자로 인정한다.** 그 문자열이 확인 토큰이다.

이 저장소의 흐름은 네 단계다.

**토큰을 만들어 저장한다.** 가입 시점에 랜덤 문자열을 만들고 24시간짜리 만료를 붙여 저장한다. 저장할 때 원본이 아니라 해시를 넣는다.

```java
// RegistrationExecutor
var rawToken = secureTokens.newToken();
emailVerificationRepository.save(new EmailVerification(
        secureTokens.hash(rawToken),   // 원본이 아니라 해시
        member.id(),
        clock.instant().plus(verificationTtl)
));
```

**그 원본을 링크에 담아 메일로 보낸다.** 원본이 존재하는 곳은 이 링크 하나뿐이다.

```
http://localhost:5173/verify?token=a3f9c2d4e8b1...
```

**사용자가 링크를 클릭하면 프론트가 토큰을 꺼내 서버로 보낸다.** URL에서 읽어 POST 본문에 담아 보내고, 처리 후 주소창을 정리한다.

**서버가 토큰을 소진하고 계정을 활성화한다.** 토큰은 일회용이며 24시간 뒤 만료된다([PD-0001-R6](../docs/policy/pd-0001-signup-and-email-verification.md)).

## 링크에 담긴 것은 비밀이다

첫 단계의 `secureTokens.hash(rawToken)`을 눈여겨볼 만하다. **비밀번호를 다루는 방식이다.** 해시로 저장하면 DB가 통째로 유출돼도 원본을 복원할 수 없다.

즉 이 코드는 이미 판단을 내려 두었다. **확인 토큰은 유출을 전제하고 보호해야 하는 비밀이다.** 그 값을 손에 넣은 사람은 소유자로 인정받기 때문이다.

그런데 그렇게 감춘 원본이 URL의 쿼리스트링에 실려 나간다. **저장 시점의 판단과 전달 시점의 판단이 어긋나 있었다.** 이 어긋남이 이 문제의 실체이고, 아래 세 갈래 유출은 그것이 밖으로 드러난 형태다.

## URL은 비밀을 담는 그릇이 아니다

문제의 뿌리는 한 문장으로 정리된다.

URL은 **목적지를 나타내는 주소**다. 비밀을 담으라고 만들어진 자리가 아니다. 그래서 웹 인프라 전체가 URL을 **기록하고, 복사하고, 다른 데로 보내는 것을 기본 동작으로 삼는다.** HTTP 요청 본문이나 헤더에는 그런 관성이 없다.

이 하나의 사실에서 유출 경로 셋이 갈라져 나온다.

## 경로 A — 웹 서버 접근 로그

웹 서버는 받은 요청을 기록한다. 기록에는 **요청 URL 전체**가 들어간다. nginx의 기본 로그 포맷이 그렇고 CDN·로드밸런서·WAF도 같다. 설정 실수가 아니라 기본 동작이다.

```
192.0.2.10 - - [23/Aug/2026:10:14:22] "GET /verify?token=a3f9c2d4e8b1... HTTP/1.1" 200
```

무게는 셋에서 온다.

**로그가 토큰보다 오래 산다.** 토큰 수명은 24시간이고 접근 로그 보관은 통상 수 주에서 수 년이다.

**로그 접근 권한이 DB 접근 권한보다 넓다.** 수집기로 흘러가고, 백업되고, 장애 분석 때 덤프로 공유된다.

**토큰이 소진되지 않은 채 로그에 남는 경우가 흔하다.** 이게 가장 반직관적인 부분이라 따로 볼 만하다.

### "일회용인데 이미 써버린 것 아닌가"

자연스러운 반문이다. 로그가 찍히는 시점에는 사용자가 방금 링크를 눌렀으니, 곧 토큰이 소진되어 로그에 남은 값은 무용지물이 될 것 같다.

그렇지 않은 이유는 **로그를 남기는 요청과 토큰을 소진하는 요청이 서로 다르기 때문이다.** 로그를 남기는 것은 페이지를 가져오는 `GET`이고, 토큰을 소진하는 것은 그 뒤에 자바스크립트가 보내는 `POST`다. 둘 사이가 벌어지는 상황이 흔하다.

| 상황 | 로그에 남나 | 토큰이 소진되나 |
| --- | --- | --- |
| 정상 클릭 | ○ | ○ (수백 ms 뒤) |
| 메일 보안 스캐너·링크 미리보기 | ○ | ✗ — **자바스크립트를 실행하지 않는다** |
| 스크립트 로드 실패, 즉시 탭 닫기 | ○ | ✗ |
| API 호출 실패 | ○ | ✗ |

아래 세 줄에서 토큰은 로그에 평문으로 남은 채 만료까지 유효하다. 그리고 링크 스캐너(Outlook Safe Links, Slack 링크 미리보기)는 기업 메일 환경의 예외가 아니라 기본이다.

## 경로 B — Referer 헤더

브라우저는 어떤 페이지에서 나가는 요청에 **"나 이 페이지에서 왔다"** 는 정보를 붙인다. `Referer` 헤더다. 원래 용도는 유입 경로 분석과 이미지 도용 차단이며, **링크 클릭뿐 아니라 이미지·스크립트·폰트를 불러올 때도 붙는다.**

이 저장소에서 이 경로가 실재한다. 스토어프론트가 상품 이미지를 `images.unsplash.com`에서 가져오고, 화면이 단일 페이지 애플리케이션이라 `/verify` 경로로 들어와도 같은 컴포넌트가 상품 목록을 그린다. 그래서 확인 링크를 열면 외부 호스트로 이미지 요청이 나간다.

```
GET /photo-1521572163474-... HTTP/1.1
Host: images.unsplash.com
Referer: http://localhost:5173/verify?token=a3f9c2d4e8b1...
```

우리 토큰이 **우리가 지울 수도, 조회할 수도, 보관 기간을 알 수도 없는 남의 로그**에 들어간다.

## 경로 C — 브라우저 이력과 사람의 복사

URL은 주소창에 뜨고 방문 이력에 들어간다. 프론트가 확인을 마친 뒤 `history.replaceState`로 주소창을 정리하지만, 이 정리는 **스크립트가 실행되고 API 응답을 기다린 뒤에야** 돌아간다. 그 전에 이미 이력·세션 복원·브라우저 동기화에 들어갔을 수 있고, 스크립트가 실패하면 아예 정리되지 않는다.

그리고 사람은 "이거 왜 안 돼요?" 하며 주소창을 복사해 채팅에 붙여넣는다. URL은 아무 경계심 없이 복사되는 물건이다.

## 예상과 달랐던 것

백로그 항목은 이 문제를 **Referer 유출**로 기록했고, 대응 순서까지 적어 두었다. `Referrer-Policy: no-referrer` 헤더를 먼저 넣고 프래그먼트 전환은 나중에 판단하자는 것이었다. 한 줄이면 되고 즉시 효과가 있다는 판단이었다.

확인해 보니 **그 순서가 뒤집혀 있었다.**

`Referrer-Policy`는 Referer에 URL을 얼마나 담을지 정하는 브라우저 설정이다. 값에 따라 전체를 보내기도 하고 오리진만 보내기도 하며 아예 보내지 않기도 한다. 중요한 것은 **기본값이 2020~2021년에 바뀌었다**는 점이다.

| 정책 | 크로스오리진 요청에 담기는 것 |
| --- | --- |
| `no-referrer-when-downgrade` (**옛 기본값**) | URL 전체 — 토큰 포함 |
| `strict-origin-when-cross-origin` (**현재 기본값**, Chrome 85 / Firefox 87) | 오리진만 — `http://localhost:5173/` |
| `no-referrer` | 아무것도 보내지 않음 |

즉 **헤더가 막으려던 경로는 우리가 아무것도 하지 않아도 이미 막혀 있었다.** 브라우저가 경로와 쿼리를 떼고 보낸다.

그리고 헤더는 **경로 A를 전혀 막지 못한다.** Referrer-Policy는 브라우저가 다른 서버에 무엇을 알려줄지를 정하는 것이지, 우리 서버가 받은 요청을 어떻게 기록할지와는 상관이 없다.

정리하면 이렇게 된다.

| | 접근 로그 (A) | Referer (B) | 이력 (C) |
| --- | --- | --- | --- |
| 손대지 않았을 때 | ✗ 샌다 | △ 브라우저 기본값이 막는 중 | △ 늦게 지워진다 |
| 헤더만 넣었을 때 | ✗ 그대로 | ○ | △ 그대로 |

**헤더 한 줄을 넣고 항목을 닫았다면 가장 무거운 경로가 그대로 남았을 것이다.** 그리고 겉보기에는 조치가 끝난 상태가 된다.

## 피해는 얼마나 큰가

과장하지 않는 편이 낫다. 이 토큰이 하는 일은 계정 활성화 하나이며 세션을 발급하지 않는다. 유출돼도 계정 탈취가 되지 않는다.

성립하는 시나리오는 계정 선점이다. 공격자가 피해자의 주소로 가입하면(비밀번호는 공격자가 정한다) 확인 메일은 피해자에게 간다. 피해자가 무시하면 그 계정은 정상적으로는 영영 활성화되지 않는데, 로그에서 토큰을 읽으면 **피해자의 주소를 단 계정을 활성화**할 수 있다.

**고쳐야 하는 진짜 이유는 다른 데 있다.** `/verify?token=` 이라는 형태는 다음에 **비밀번호 재설정 링크나 로그인 링크가 놓일 자리**다. 그때 같은 경로는 계정 완전 탈취가 된다. 지금 바로잡는 비용은 파일 두 개이고, 나중에 바로잡는 비용은 이미 발송된 링크와 그때까지 쌓인 로그 전부다.

## 프래그먼트가 이 문제를 푸는 이유

URL에서 `#` 뒤에 오는 부분을 프래그먼트라고 한다. 원래 용도는 문서 안의 특정 위치를 가리키는 것이다 — `#section-3` 같은 앵커가 그것이다.

여기서 중요한 성질은 **브라우저가 프래그먼트를 서버로 보내지 않는다**는 점이다. 문서 안 어디로 스크롤할지는 서버가 알 필요가 없기 때문이며, 규격상 요청 라인에 포함되지 않는다. 서버는 프래그먼트가 있었다는 사실조차 알지 못한다.

```
http://localhost:5173/verify?token=a3f9c2...   서버가 본다. 로그에 남는다
http://localhost:5173/verify#token=a3f9c2...   서버는 "/verify"만 본다
```

같은 이유로 **Referer 헤더에서도 제거된다.** 그래서 토큰을 프래그먼트로 옮기면 **경로 A와 B가 한 번에 닫힌다.**

`Referrer-Policy` 헤더는 함께 넣지 않았다. 프래그먼트에 있는 토큰은 애초에 Referer에 실리지 않으므로 헤더가 추가로 막는 것이 없다. 다만 여기에는 받아들인 위험이 하나 있다. **브라우저 기본값은 보장이 아니다** — CDN이 정책을 느슨한 값으로 내려주거나 개별 요소에 `referrerpolicy="unsafe-url"`이 붙으면 조용히 되돌아간다. 그 경우에도 프래그먼트에 있는 토큰은 새지 않지만, 되살아나는 것은 이 저장소가 통제하는 성질이 아니다. 정적 호스트 설정이 저장소에 생기는 시점을 재검토 조건으로 남겼다.

경로 C는 닫지 않았다. 프래그먼트도 주소창에 뜨고 이력에 들어간다. 세션을 발급하는 토큰을 링크로 보내게 될 때 다시 볼 일이다.

## 하네스가 보지 못하던 것

링크 형식을 고정하는 테스트가 **하나도 없었다.** `#`를 `?`로 되돌려도 `make verify`가 통과했다. 이 수정을 유지하는 장치가 문서 말고는 없는 상태였다는 뜻이다.

테스트를 추가하면서 단언을 짝으로 뒀다. 프래그먼트를 요구하는 것과 쿼리스트링을 금지하는 것이다. 앞의 것만 있으면 링크가 하나 더 붙는 식으로 쿼리 경로가 되살아나도 걸리지 않는다.

추가한 뒤 `#`를 `?`로 되돌려 실제로 실패하는지 확인했다.

```
VerificationLinkTest > neverPutsTokenInQueryString() FAILED
VerificationLinkTest > putsTokenInFragment() FAILED
```

통과만 확인한 테스트는 통과만 하는 테스트일 수 있다.

이 사각지대는 처음이 아니다. [problem/001](001-read-triggers-write.md)에서는 인메모리 대역이 검증 대상과 같은 가정을 공유해 저장 누락을 놓쳤고, [problem/002](002-positional-jdbc-binding.md)에서는 왕복 테스트가 쓰기와 읽기의 대칭 오류를 상쇄해 컬럼이 뒤바뀐 채로 전부 통과했다. 여기서는 아예 단언이 없었다. **세 번 다 초록불이 무언가를 보증한다고 믿었는데 그 무언가가 검증 대상에 들어 있지 않았다.**

## 배운 것

**"이 경로가 실재한다"와 "이 경로가 지금 새고 있다"는 다르다.** 백로그가 지목한 Referer 경로는 실재했지만 브라우저 기본값이 막고 있었다. 대응을 정하기 전에 어느 것이 실제로 열려 있는지 확인해야 순서가 뒤집히지 않는다. 실재 여부만 보고 대응하면 조치는 끝났는데 위험은 남는 상태가 만들어진다.

**기본값에 기대는 보호는 보호의 부재와 다르지만 보장과도 다르다.** 브라우저 기본 정책은 우리가 통제하지 않는다. 이번에는 프래그먼트가 그 위험까지 함께 없앴지만, 그런 선택지가 없는 상황에서는 명시하는 쪽을 골라야 한다.

**한 시스템 안에서 같은 값을 다른 무게로 다루고 있으면 그 자체가 신호다.** DB에는 해시를, 로그에는 평문을 남기고 있었다. 어느 쪽이 맞는지는 더 엄격한 쪽이 답이다 — 느슨한 쪽에 맞춰 내리는 것이 아니라. 이런 불일치는 보통 두 판단이 서로 다른 시점에 내려졌기 때문에 생기고, 그래서 한쪽만 보고 있으면 드러나지 않는다.
